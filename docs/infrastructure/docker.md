# Docker и деплой

Статус: требования и целевая схема; Dockerfile, Compose и bootstrap пока отсутствуют.

## Стадии

Три именованные стадии каждого применимого Dockerfile:

```dockerfile
# Схема наследования, не готовый Dockerfile
FROM <pinned-image> AS base
# общие зависимости и окружение конкретного компонента
FROM base AS dev
# инструменты разработки, линтеры, тесты, hot reload
FROM base AS prod
# production-зависимости и результат сборки
```

`dev` и `prod` напрямую наследуются от `base`, а не друг от друга. У бэкенда и
фронтенда свои базовые образы; это не требование поместить Python и Node в один образ.
Как собирать и обслуживать фронтенд при такой схеме, выбирается до реализации
контейнеров. Схема выше не исполняется и содержит условное имя образа.

## Окружения

- **Dev:** исходники подключаются в контейнеры, поддерживаются перезапуск API
  и Vite; доступны uv и frontend-инструменты проверки.
- **Prod:** production-конфигурация без hot reload и bind mount исходников;
  сборки воспроизводимы, lock-файлы и версии образов закреплены.
- Сборка, установка зависимостей приложения, тесты, форматирование и запуск
  выполняются в контейнерах. На хост не требуется ставить Python/Node/FFmpeg.
- Docker Compose объединяет API, worker, фронтенд/HTTP-вход, PostgreSQL, Valkey
  и RustFS. Конкретные имена сервисов будут зафиксированы в конфигурации.
- PostgreSQL и RustFS получают постоянные тома. Valkey остаётся потеряемым;
  задания восстанавливаются по [архитектуре](../backend/architecture.md).
- Постоянные данные не удаляются обычным повторным запуском или деплоем.
  Порты БД, Valkey и RustFS не открываются в интернет без необходимости.
- Секреты передаются конфигурацией окружения, не встраиваются в образы и Git.
  Доступность сервисов проверяется healthcheck и повтором подключения, а не
  только порядком старта контейнеров.

## CLI управления ролями

Назначение ролей выполняется CLI-командой внутри контейнера бэкенда по email
зарегистрированного аккаунта. Политика и права — в [User](../backend/modules/user.md).
Так назначается и первый администратор; UI пока не требуется.
CLI должна быть доступна в production-окружении. Точная команда будет добавлена
после реализации и проверки, сейчас готовой команды нет.

## Деплой одной командой

Цель команды: проверить целевую Ubuntu, подготовить Docker/Compose, если их нет,
создать необходимые конфигурацию и секреты, поднять постоянные сервисы,
выполнить миграции и запустить приложение, проверить доступность.
Повторный запуск должен сохранять данные. Настройка секретов не должна требовать
ручного редактирования контейнеров. Это цель, а не уже выполненная возможность.

Версия Ubuntu, источник установки Docker, права bootstrap, домен/TLS, конфигурация
внешнего HTTP-входа и объём ресурсов — [Q09](../tasks/open-questions.md).
Значения не выбраны; рабочая команда будет добавлена только после реализации
и проверки на чистой целевой VM.

Проверка готовности: чистая VM → одна команда → регистрация/вход → загрузка
небольшого видео → готовый HLS → просмотр, затем повтор команды и перезапуск
с подтверждением сохранности данных. Отдельно проверяется восстановление
обработки после потери Valkey.
