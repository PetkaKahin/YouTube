# ADR-0028: расширение starsessions для конкурентных запросов

Статус: принято пользователем и реализовано 2026-11-13; Q25 закрыт в T02.

## Решение

- Сохранить starsessions 2.2.1. Повторная проверка PyPI/GitHub: стабильный релиз
  по-прежнему 2.2.1, новее есть только 2.3.0a1. В alpha и основной ветке RedisStore
  всё ещё выполняет безусловный SET; issue №58 открыт.
- Расширение находится в нашем `common`, без изменений site-packages, форка,
  monkey patch и копирования реализации middleware библиотеки.
- Один экземпляр адаптера SessionStore на запрос. Новая запись создаётся с NX,
  прочитанная действующая сессия обновляется только с XX. Исчезнувший ключ
  не создаётся заново ни после удаления, ни после TTL/потери данных Valkey.
- При ротации ID генерирует starsessions. Для существующей сессии Valkey атомарно
  переносит запись под новый ID только если старый ключ ещё существует и новый
  свободен. Старый ключ становится недействительным сразу. Конкурирующая поздняя
  ротация получает 409; она не переносит отозванный снимок под новый ID.
- Для новой анонимной сессии ротация резервирует новый библиотечный ID пустой
  записью с TTL. Финальное сохранение обновляет её с XX: потеря записи между
  ротацией и ответом не восстанавливает аутентификацию.
- HTTP-обёртка использует штатный SessionMiddleware и удаляет только сессионный
  Set-Cookie, если сохранение/удаление отклонено. Другие cookie и поток не буферизуются.
  Повторное удаление в одном запросе идемпотентно и сохраняет результат первого.
- Ответы >=400 не сохраняют новые данные и не продлевают сессию; неуспешный
  сценарий не выдаёт авторизованную cookie из частично изменённого снимка.
- Без распределённых блокировок вокруг всего запроса. Сериализация, генератор ID,
  rolling 30 дней и формирование cookie остаются библиотечными. БД, бизнес-логика
  и прикладные HTTP-маршруты не меняются.

## Границы

Первое успешное удаление/перенос старого ключа определяет результат гонки;
запросы, начатые с этим ID, не могут создать новую авторизованную сессию
без новой аутентификации. Уже начатый бизнес-сценарий не откатывается выходом,
проверки прав остаются ответственностью бизнес-задач.

Сохранение, которое Valkey принял до отзыва, могло уже начать HTTP-ответ.
Отозвать отправленный заголовок или гарантировать порядок доставки по разным
HTTP-соединениям сервер не может; такой ID всё равно недействителен на сервере.
Подавление cookie относится к записи, отклонённой после отзыва/истечения.
Реализация рассчитана на согласованный одиночный Valkey, не Redis Cluster.

При обновлении starsessions сначала прогнать конкурентные проверки. Когда
штатный механизм обеспечит те же гарантии, расширение можно удалить отдельно.

## Приёмка

Реальные Valkey и HTTP: выход/ротация против удержанного запроса, две ротации,
поздний выход, TTL и удаление между загрузкой и сохранением, согласованный rolling
срок, несколько экземпляров приложения, отмена запроса, сбой хранилища и стриминг.
Регрессии существующих HTTP/DI/Tach проверяются общим docker/run check.

Результат: полный `docker/run check` прошёл — 203 теста, в том числе 18 новых
проверок сессий; типы, линтинг, Tach и аудит зависимостей без замечаний.
Production wheel проверен через настоящий HTTP-сервер: создание, чтение, ротация,
выход, Secure cookie, readiness, Swagger/OpenAPI, Alembic и завершение lifespan.
Проверены секреты dev и все четыре контекста Docker; утечек не обнаружено.
