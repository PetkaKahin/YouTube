# ADR-0025: Dishka для DI

Статус: принято пользователем и реализовано для технических зависимостей в T02, 2026-11-13.

Дополнение: способ подключения модульных провайдеров выбран в
[ADR-0027](0027-explicit-module-providers.md). Q29 закрыт; ограничения ниже
об отсутствии разрешения на регистрацию описывают состояние до этого решения.

## Решение

- Использовать Dishka: async-контейнер, провайдеры, области жизни `APP` и `REQUEST`.
- Настройка контейнера существующих технических зависимостей находится в `app`.
  Существующий lifespan ресурсов оборачивается провайдером `APP`;
  контейнер закрывается при остановке и неудачном запуске приложения.
- `AsyncSession` создаётся в области запроса/операции и закрывается при выходе
  из неё. DI не делает автоматический commit: транзакцией управляет сценарий.
- HTTP-контроллеры используют готовую интеграцию FastAPI; вне HTTP область
  операции можно открыть через тот же контейнер обычным async context manager.
- `domain/application/public` не импортируют Dishka и не получают DI-маркеров.
  Их обычные конструкторы принимают абстракции; реализации задают провайдеры.
- Для проверки основы не создаются фиктивные бизнес-сценарии и провайдеры
  несуществующих реализаций. Подключаются только уже имеющиеся ресурсы и сервисы.

## Граница решения

Библиотека выбрана, но она не отменяет правило внешнего доступа только через
`public` из [ADR-0024](0024-public-dependencies.md). Автоматическое обнаружение,
скрытые импорты, регистрация через `__init__` и исключения для `app` не согласованы.
Способ подключения будущих инфраструктурных провайдеров бизнес-модулей
остаётся Q29 до их реализации. Подключение текущих технических провайдеров
`app` не требует доступа к бизнес-модулям и не зависит от этого выбора.

## Проверка

В Docker на Python 3.14 и текущих FastAPI/Starlette проверены:
получение зависимости контроллером, отдельные области запросов,
общие APP-ресурсы, освобождение при успехе/ошибке/стриминге, rollback сессии,
использование вне HTTP, проверка графа и прежние ограничения Tach.
Полный `docker/run check`: 144 теста, типы, линтинг, аудит зависимостей и HTTP smoke.
