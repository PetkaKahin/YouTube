# ADR-0062: серверное управление повторами фоновых заданий

Статус: бизнес-правила приняты пользователем; серверная часть T12 реализована.

Ручной повтор заново ставит зарегистрированную работу с обычной политикой
ADR-0035: до трёх запусков при временных ошибках. История не удаляется.
Доступ имеет только актуальный admin; постановки и исполнитель прослеживаются.
Поддерживаются одна джоба, выбранные и все упавшие. Пересекающиеся запросы
не дублируют одну неуспешную работу. Повтор её новой неуспешной постановки —
новая работа с новым ID и новой историей.

Реализация сохраняет намерение в PostgreSQL, не вставляя все джобы в очередь
в HTTP-транзакции. Для «все» сохраняется граница истории на момент запроса;
перебор выполняется порциями. Новые ошибки в этот запрос не включаются.
Параметр `JOB_RETRY_BATCH_SIZE` в `.env` — число джоб в порции, по умолчанию 20,
положительное целое. Из него вычитается число todo/doing соответствующей очереди,
чтобы при её заполнении подача повторов ожидала свободных мест.
Обычные постановки не ограничиваются этим механизмом. Порог 100 и отдельный
интервал 15 секунд не вводятся. Подачу вызывает существующее обслуживание;
оно переживает рестарт и потерю Valkey. Параллелизм worker не меняется.

История ошибок — новые сверху по occurred_at/id, без фильтров; все списки
используют cursor по 20 по ADR-0059. Ошибки после успеха также видны.
HTTP не принимает имена функций, аргументы, ключи медиа или приоритеты.
Video восстанавливает свою работу через собственный public-порт; технический
диспетчер не читает таблицы Video. Неизвестные/устаревшие/недоступные задания
не исполняются; результат каждого рассмотренного задания виден в запросе повтора.
Успешные медиа не перекодируются и не меняют публикацию, скрытие, права и даты.

Серверная часть не зависит от T09; интерфейс админки остаётся T12/UI.
