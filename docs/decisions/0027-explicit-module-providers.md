# ADR-0027: явное подключение провайдеров модулей

Статус: принято пользователем и реализовано 2026-11-13. Закрывает Q29 о способе подключения DI;
уточняет запрет внешнего доступа из ADR-0023/0024 и границу ADR-0025.

## Решение

- Провайдер Dishka каждого модуля находится в `<module>/infrastructure/di.py`.
  Он связывает порты с реализациями и регистрирует сценарии своего модуля.
  По умолчанию используется REQUEST; APP задаётся для конкретных долгоживущих
  зависимостей. Провайдер не открывает соединения при импорте или создании.
- `app/module_providers.py` явно импортирует только классы провайдеров пяти модулей
  и возвращает их экземпляры. `app/di.py` добавляет их в общий контейнер вместе
  с техническими провайдерами. Автообнаружение, entry points и регистрация через
  побочные эффекты `__init__` не используются.
- Это узкое техническое исключение: только реестр может напрямую импортировать
  `<module>.infrastructure.di`, и только класс провайдера. Репозитории, ORM-модели,
  сценарии и остальные внутренние файлы для него закрыты.
- Контроллеры и прочие бизнес-потребители сохраняют доступ только через `public`.
  `public` по-прежнему импортирует только собственные domain/application и stdlib.
  Сценарии принимают абстракции конструкторами; они не знают контейнер и провайдеры.
- При добавлении модуля меняются явный реестр и границы Tach. При замене адаптера
  внутри существующего модуля меняется только его провайдер/инфраструктура.
- Бизнес-тесты внутри модуля могут использовать и проверять его провайдер;
  им также доступны его внутренние помощники. Провайдер не доступен тестам
  и инфраструктуре других модулей.

## Объём текущего этапа

Подключены пять провайдеров без вымышленных сценариев и адаптеров.
БД, бизнес-логика и HTTP-контракты не меняются; бизнес-таблиц и новой миграции нет.
При появлении ORM-моделей их техническую регистрацию нужно реализовать вместе
с моделями, сохраняя `public` независимым от ORM и закрытые репозитории.

## Проверка

Tach должен пропускать импорты классов провайдеров из реестра и их зависимости
от собственных слоёв. Контроллеры, common, public, чужие модули и общие тесты
не получают прямого доступа к провайдерам. Реестру запрещены остальные
внутренности и непубличные символы технической точки входа.
Поведенческая проверка должна подтвердить, что зарегистрированный внутри модуля
сценарий разрешается общим контейнером через его публичный контракт.

Проверки реализованы в `backend/tests/test_architecture.py`: для каждого из пяти
модулей отдельная копия исходников получает тестовый порт, адаптер и сценарий;
настоящая фабрика контейнера разрешает сценарий по публичному контракту и сохраняет
области жизни. В production-пакетах этих тестовых реализаций нет.
Полный `docker/run check`: 185 тестов, в том числе 137 архитектурных;
типы, линтинг, аудит зависимостей и HTTP smoke прошли. Dev/prod Python собраны;
prod API запущен с реальными хранилищами, readiness/Swagger/OpenAPI работают.

Основание выбора: фиксированный набор бизнес-модулей, простой обозримый состав
приложения и статический контроль импортов. Исследование альтернатив сохранено
в [библиотеках](../backend/libraries.md#подключение-провайдеров-исследование-q29).
