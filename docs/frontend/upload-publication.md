# Подтверждение публикации

F25 — `done` по функциональному профилю Chromium/Firefox. [Общий сценарий](upload.md)
связывает [метаданные F22](upload-start.md), [передачу F23](upload-transfer.md)
и [обработку F24](upload-processing.md). Внешний вид проверяет пользователь,
снимки и сравнение оформления не выполнялись.

## Подтверждение и просмотр

[VideoUpload](../../frontend/src/widgets/video-upload/ui/VideoUpload.vue) выполняет
POST publish после принятия исходника и сохранения параметров видео. Пока запрос
идёт, показано «Подтверждаем публикацию…», повторная отправка заблокирована.
Готовый черновик до публикации не получает ссылку просмотра.

Ответ publish проверяется по точным ID видео/владельца, publication=published
и upload=uploaded. HTTP 200 с другим состоянием не попадает в кэш настроек
и не включает «Сохранено». После подтверждения File очищается, состояние
обработки перечитывается отдельно. Если готовых вариантов ещё нет, показано
ожидание готового видео; после доступного варианта появляется обычная ссылка
просмотра с точным ID. Private сохраняет ограничения, hidden не получает
ссылку и имеет явное сообщение о недоступности. Ошибка чтения готовности
не заменяется прежним успешным результатом — F24.

Неуспешный или потерянный ответ publish оставляет форму без подтверждения.
Явный повтор использует тот же ID, сохраняет метаданные и пропускает уже
принятый исходник: нет нового черновика, PUT частей или complete. Если сервер
успел зафиксировать публикацию до обрыва, повтор подтверждает её идемпотентно.
Создание черновика автоматически не повторяется.

Восстановленный URL читает подтверждённое состояние с сервера. Изменение
названия/описания/доступа снимает прежнее «Сохранено» и возвращает действие
сохранения. Это позволяет сохранить правки опубликованного видео в той же форме.
После закрытия открывается соответствующий каталог Studio.

Даты не рассчитываются клиентом: created_at остаётся датой создания черновика
и используется в каталоге, added_at назначается при подтверждении исходника.
Публикация не заменяет эти даты. Повтор publish без правок сохраняет также
updated_at. Правила сервера — [B11/B22](../backend/media-delivery.md).

## Проверки

В Docker прошли vue-tsc/Vite build, ESLint/Prettier виджета и синтаксис/
форматирование [upload-publication.mjs](../../docker/browser/upload-publication.mjs).
Регрессия обработки на итоговом виджете — upload-processing.mjs, по **39 проверок**
в Chromium и Firefox, прошла.
Chromium и Firefox выполнили по **35 функциональных проверок**:

- Настоящие создание, передача, приём и public-публикация по одному точному ID;
  сохранены created_at/added_at, в каталоге отображается исходная дата создания.
- При processing=pending публикация сохранена, просмотр не обещается;
  после настоящей готовности ссылка появляется, гостевой GET просмотра успешен.
- Восстановление опубликованного видео и сохранение изменённых метаданных
  без нового черновика или ложной старой отметки «Сохранено».
- Настоящий готовый private-черновик до publish недоступен; удержанный publish
  не выглядит успехом, повторные submit не создают команд/передач.
- После поздней private-публикации владелец получает просмотр, гость и аккаунт
  без разрешения — 404; private отсутствует в публичной ленте и поиске.
- 503 publish и повтор без новой передачи; HTTP 200 с draft, непринятым upload
  или чужим владельцем не подтверждает успех клиента, повтор использует тот же ID.
- Разрыв ответа после настоящего commit: клиент не сообщает успех, явный повтор
  подтверждает серверное состояние и сохраняет все даты.
- Настоящий CSRF 403 с сохранением draft и успешным повтором; настоящее hidden
  недоступно даже владельцу, повтор publish не снимает скрытие/не меняет added_at.
- Поздний ответ после закрытия не заполняет новую форму; телефон показывает
  ожидание и подтверждает private; настоящий 401 при publish очищает форму
  и оставляет черновик неопубликованным.

Успешная запись выполняется через настоящие API/PostgreSQL/Valkey/Nginx/RustFS
и worker изолированной fixture. Прокси вводит 503, задержки, обрыв после commit,
неверные поля ответа publish и processing=pending. Последний проверяет реакцию
клиента на раннюю публикацию по DTO; фактическая гонка публикации с кодировщиком
покрыта B11/B18. Поздняя публикация проверена после реального готового качества.
Медиабайты всех HLS-маршрутов здесь повторно не декодируются — это B22/F12–F14.
Новых серверных команд, SQL/медиапарсеров или библиотек нет.
Проверены сессия/CSRF, private/hidden, отсутствие запрещённой публикации после
отказа, повторы/поздние ответы, точные ID и вывод метаданных как текста.

## Повтор и ограничения

Запуск — по [общему профилю загрузки](upload.md#проверки), fixture
`--media --links --upload`, браузер `/checks/upload-publication.mjs`, Firefox —
`--firefox`. Нужны mounts `/checks`, `/work` с manifest и `/media`; используется
скачанный portrait.mp4, новые материалы не генерируются. Браузеры запускаются
последовательно. SIGINT fixture удаляет её медиа, сессии и БД, рабочие данные
не меняются. Диагностика не печатает подписанные URL и приватные поля формы.

Бэкенд и контракт не менялись. Safari/WebKit и физический телефон не
квалифицированы; полный make check остаётся до завершения всего плана.
