# Прогресс просмотра: требования к бэкенду

Статус: бэкенд реализован, миграция 0026 применена в dev. Метод и DTO доступны
в OpenAPI; запись и полосы аккаунта [подключены на фронте](hover-preview.md).
Правила согласованы пользователем 2026-11-17;
[реализация и профильные проверки](../backend/watch-progress.md).

## Согласовано

- Сохраняется последняя позиция основного плеера, включая перемотку назад.
- Для аккаунта прогресс постоянный и общий между устройствами; для гостя — локальный
  в текущем браузере. Предпросмотр карточки не меняет позицию основного плеера.
- На обычной карточке показана полоса просмотренной части. У предпросмотра свой
  интерактивный ползунок перемотки. Первоначальный R18 не добавлял продолжение;
  пользователь отдельно запросил его 2026-11-18 — [клиентское восстановление](resume.md),
  без нового серверного контракта.

## Контракт

1. PUT `/api/v1/videos/{video_id}/progress`, сессия + CSRF, body:
   `{"position_seconds": 123.5}`. Ответ 200:
   `{"position_seconds":123.5,"duration_seconds":600.0,"updated_at":"..."}`.
   Отрицательное/нечисловое/не finite значение — 422. Длительность берётся
   из доверенных данных видео; превышение из-за округления HLS ограничивается концом.
   Возвращается фактически сохранённая позиция. Последняя принятая запись заменяет
   предыдущую, максимум просмотренного не вычисляется. Ноль и перемотка назад допустимы.
2. В `FeedCardResponse` и `VideoDetailsResponse` добавить
   `watch_progress: {position_seconds, duration_seconds, updated_at} | null`.
   Для гостя и ещё не просмотренного видео — null. Общая карточка покрывает ленту,
   видео в поиске, публичный список канала и состав плейлиста; значения читаются пакетно для страницы,
   без запроса на каждую карточку и N+1. В служебный `VideoViewResponse` поле не нужно.
3. Обычные проверки просмотра применяются и к записи прогресса: 401 без сессии,
   404 для недоступного/скрытого/неопубликованного/не готового видео. Прогресс
   не выдаёт разрешение на видео и не раскрывается другому аккаунту. Входящие
   user_id/role/duration и неизвестные поля не принимаются.
4. Cookie/CSRF, no-store/Vary: Cookie и точные int64 — как у существующих API.
   Прогресс не меняет метаданные/updated_at видео, дату добавления, порядок выдач,
   лайки, состояние обработки или модерацию. Чтения, предпросмотр и служебное
   воспроизведение не создают записей прогресса.
5. Метод и DTO опубликованы в OpenAPI. Фронт сгенерировал типы через
   Hey API и подключил запись/полосы аккаунта. Авторизованному пользователю
   не подставляется гостевой прогресс.

Фронт ограничивает регулярные записи основного плеера, а также сохраняет позицию
на паузе, перемотке, завершении и уходе. Уход страницы — best effort, не гарантия
доставки; сервер не должен зависеть от единственного финального запроса браузера.
Гостевые позиции не сливаются с аккаунтом автоматически. История просмотров,
отдельная страница истории, счётчик просмотров и рекомендации не запрашиваются.
Это граница исходного R18; история отдельно запрошена пользователем в
[R19](library-backend-request.md), без счётчика просмотров и рекомендаций.

## Регрессия состава плейлиста при подключении фронта

2026-11-17 в реальном изолированном API воспроизведён 500 у
GET `/api/v1/playlists/{playlist_id}` с непустым составом. В
`backend/src/app/http/playlists.py` создаётся `FeedCardResponse` без нового
обязательного поля `watch_progress`; сериализация отклоняет ответ.

Блокер исправлен: nullable поле проходит через Video.public → DTO Channel → HTTP.
Позиции читаются одним запросом после отбора доступной страницы; гостю и
непросмотренному видео возвращается null. Права, порядок и cursor сохраняются.
В Docker прошли 6 профильных HTTP-проверок непустого плейлиста, изоляции позиций,
прав, пакетного чтения и отказа БД без частичного ответа.
[Реализация и проверка](../backend/watch-progress.md#состав-плейлиста).

Фронтенд повторно проверил исправленный ответ и полосу плейлиста в Chromium
и Firefox: по 33 профильные проверки R18 прошли; ветка принятия 500 удалена.
