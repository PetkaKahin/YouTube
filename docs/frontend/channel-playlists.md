# Канал и состав плейлиста

F18 — `done` по [функциональному профилю публичного канала](channel-page.md).
F19 — `done` по [функциональному профилю подписки](subscriptions.md).
F20 — `done` по [функциональному профилю состава и прямых ссылок](playlist-contents.md).
Прямые адреса плейлистов подключены; общая приёмка ещё впереди.
Свой канал сохраняет обычный публичный интерфейс; личный список и создание
размещены в [Studio](studio.md).

## Маршруты и данные

`/@<tag>` и `/@<tag>/videos` открывают видео канала, `/@<tag>/playlists` —
его public-плейлисты. Вкладка и выбранный плейлист сохраняются в URL;
`/@author/playlists?list=<id>` раскрывает состав на том же канале, без нового
самостоятельного экрана. Переходы из поиска используют известный тег автора.
Прямой `/playlist?list=<id>` получает разрешённый ответ с channel по Q49 и
через `router.replace` открывает тот же состав на канале. История не получает
лишний промежуточный адрес. Автор не определяется по первому видео: пустые
public/unlisted/private-плейлисты используют серверные данные канала.

Профиль, видео и плейлисты получаются отдельными запросами Hey API/TanStack Query.
Ключи содержат область сессии, канонический тег и ID канала у списков;
ID остаются точными строками. Запросы ждут подтверждения сессии, невыбранный
каталог не сохраняет прежний снимок — [жизненный цикл F18](channel-page.md).
Имя не используется как идентификатор канала. Списки продолжаются серверным
cursor по 20, с IntersectionObserver и доступной кнопкой повтора/продолжения.
Карточки дедуплицируются по ID, порядок сервера сохраняется.

Публичная часть не смешивается со списком владельца: даже ему выдаются только
public-плейлисты и опубликованные public-видео с готовым качеством.
Private/unlisted в каталоге не показываются. Метрики и изображения профиля,
которых нет в API/ТЗ, не придумываются. Без баннера используется компоновка
профиля без пустого места под отсутствующее изображение; аватар — первая буква.
Вкладки функций вне ТЗ, редактирование профиля и неработающие действия не добавлены.

Подписка — существующий `features/subscribe-channel` с общим ключом Query:
гость входит с возвратом к каналу, владелец не видит self-подписку, запись
подтверждает сервер. Кнопки канала и просмотра читают одно состояние своей пары.
Ожидание свежего состояния после перехода, ошибки и поздние ответы — [F19](subscriptions.md).

## Состав плейлиста

`widgets/playlist-contents` читает GET плейлиста и проверяет, что channel_id
совпадает с открытым каналом. Недопустимый ID, отсутствие прав и чужой контекст
не показывают название или видео под другой шапкой. Плейлист не определяет
права видео: отображаются только присланные сервером карточки, без placeholders
для скрытых объектов и без подсчёта закрытых элементов.

Порядок соответствует включению; новые элементы в конце, ручной перестановки нет.
Public/unlisted доступны по правилам сервера, private — владельцу. Каждый переход
ведёт к обычному `/watch?v=<id>`, где права проверяются заново.
Пустой доступный состав отличается от ошибки и недоступного плейлиста.
Название/описание выводятся как текст с сохранением переносов, без HTML.
Ошибка следующей страницы оставляет уже доступную часть и кнопку повтора;
отказ доступа убирает метаданные/карточки и кэш текущего плейлиста.
При уходе отмену и удаление неактивного снимка выполняет Query с gcTime 0;
новый экземпляр ждёт свежего ответа. Отложенная очистка после ухода не удаляет
замену по тому же адресу. Отказ доступа удаляет прежние данные конкретного
запроса; пустой отключённый наблюдатель не содержит закрытого снимка.
Back/Forward восстанавливают URL, содержимое и заголовок вкладки —
[проверки F20](playlist-contents.md).

Новый ответ GET с channel получен генерацией Hey API после отдельного изменения
бэкенда — [Q49](../tasks/open-questions.md#q49-канал-в-ответе-просмотра-плейлиста).
`pages/playlist-link` проверяет точные ID, соответствие channel.id/channel_id и
формат тега перед переходом; временный запрос удаляется при уходе. Неверный ID
отклоняется до API, поздний ответ не перенаправляет со следующего экрана.
При недоступности канала/названия нет в UI; гостю доступен вход с возвратом
к исходной ссылке. Ошибка проверки сессии имеет собственный повтор и не
считается гостем. API повторно проверяет доступ при открытии состава.
Бэкенд в этой работе не меняется. Создание и личный список проверены
отдельным функциональным профилем [F21](studio.md), в согласованной Studio-модалке.

## Референсы и проверка

Использованы пользовательский снимок канала и самостоятельно открытые русские
тёмные вкладки YouTube на ПК/мобильном вебе — [каталог](references.md).
На телефоне видео/плейлисты представлены строками с превью слева; кнопка
подписки занимает ширину профиля. На ПК используются сетки из референсов.
Полное сравнение до 2 CSS px ещё не завершено; встроенное раскрытие состава
сохраняет требование ТЗ «на канале», а не отдельную страницу YouTube.

Профильные проверки выполняются в Docker на отдельной БД. Режим fixture
`--media --channel` добавляет 41 публичное видео и 41 public-плейлист, а также
пустой канал, private/unlisted и недоступные элементы. Входы — прежние скачанные
материалы; дополнительные видео проходят настоящий конвейер с дедупликацией,
готовность не подставляется SQL. Скрытие для негативного сценария устанавливается
только в этой отдельной БД. Учётные записи, объекты RustFS и сессии удаляются
при остановке fixture. Рабочий `make seed` и его данные не используются.

Запуск — по [инструкции плеера](watch.md#повторить-проверку), с добавлением
`--channel` после `--media`. Затем вместо watch.mjs выполнить
`youtube-browser-check /checks/channel.mjs` с теми же mounts/network.
Проверка включает страницы 20/20/1, переходы, историю/обновление, пустые списки,
разные теги при одинаковых именах, авторизацию и фильтрацию состава, безопасный
текст, ошибку API/повтор и размеры ПК/телефона.

В Docker прошли 32 сценария Chromium и 20 Firefox на 1920×935/390×844,
vue-tsc/Vite build, ESLint, Prettier, Ruff и форматирование fixture.
Дополнительно подтверждены Back/Forward и восстановление заголовка канала
после закрытия плейлиста. При начальной подготовке fixture имя с HTML было
отклонено серверной валидацией; для проверки совпадающих имён использовано
допустимое «Общий автор». HTML-подобные заголовки плейлистов и описания
проверены настоящим DOM. Пагинация проверяется по cursor и составу, а не
требованию держать ровно 20 карточек на экране после автоматической догрузки.
Повторная проверка оболочки/аккаунта/поиска — 42 сценария Chromium прошли;
ссылка поиска сохраняет точный int64 и ведёт к составу на известном канале.
Полный `make check` не запускался: общий план фронтенда ещё не завершён.

Firefox запускается теми же mounts/network командой
`youtube-browser-check /checks/firefox.mjs --channel`.

## Проверка прямых ссылок Q49

Для профильного fixture достаточно `--media --links` вместо `--media --channel`:
создаются public, unlisted, private и пустые плейлисты без каталога из 41 видео.
В тех же Docker mounts/network запускаются `/checks/playlist-link.mjs` и
`/checks/firefox.mjs --playlist-link`. Рабочая БД не используется.

В Chromium прошли 34 сценария: прямые и пустые ссылки обоих размеров,
точные int64, независимые права видео, вход владельца/приглашённого, отсутствие
автора при отказе, очистка private после выхода, неверные/повторные ID до API,
ошибка сети/повтор, замена записи истории и отмена перехода после ухода.
Firefox прошёл 15 проверок на ПК/телефоне, включая вход по пустой private-ссылке.
Генерация Hey API, vue-tsc/Vite build, ESLint, Prettier и Ruff вспомогательных
fixture прошли. Проверки использовали настоящий изолированный API/PostgreSQL/
Nginx/RustFS; собственные БД, сессии и медиа очищены после прогона.

Ошибка превью видео теперь вызывает перепроверку публичной выдачи, а её
неактивный снимок удаляется. Реальная смена public → private на канале
проверена в [профиле главной](feed.md); остальные сценарии канала не повторялись.
