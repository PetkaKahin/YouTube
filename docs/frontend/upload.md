## Сценарий

В меню «Создать» рядом с созданием плейлиста есть «Добавить видео».
Он открывает `/studio/upload` с модалкой 960×840 CSS px на ПК.
Гость сначала входит, затем возвращается к исходному адресу. Файл выбирается
кнопкой или перетаскиванием; одновременно принимается один исходник.
Нет фильтра по расширению/MIME. Проверяется размер 1..5 000 000 000 байт,
показаны ограничения 60 минут, возможность видео без звука и ниже 360p.
Содержимое/длительность проверяет сервер, без доверия браузерным метаданным.

«Информация» содержит название и описание, имя файла и состояние справа.
Начальное название берётся из имени без последнего расширения, без обрезания
до допустимой длины. Правила: 1–100 Unicode-символов названия после trim,
описание до 5000, обычный текст, запрет NUL/некорректных surrogate.
Превышение длины сохраняет введённое значение и показывает ошибку.

«Далее» открывает «Доступ»: только public/private, без исходного выбранного
варианта. «Сохранить» последовательно выполняет:

1. POST `/api/v1/videos` с метаданными и явным доступом.
2. POST `/api/v1/videos/{id}/upload` с размером; Blob-части передаются XHR PUT
   на подписанные same-origin `/uploads/` через Nginx в RustFS.
3. POST complete подтверждает исходник. Только после него файл считается принятым.
4. Применяются [плейлисты, разрешения и передача своего превью](video-options.md).
5. POST publish подтверждает публикацию. После ответа показывается «Сохранено»;
   готовность качеств продолжает проверяться отдельно.

Подтверждение publish проверяет не только ID/владельца, но и published/uploaded.
Потеря ответа не объявляет успех; явный повтор подтверждает тот же объект без
новой передачи. Изменение метаданных восстановленного видео снимает прежнее
«Сохранено», позволяя применить правки — [F25](upload-publication.md).

Во время передачи показаны реальные байты/процент XHR; отправленные 100% не
заменяют подтверждение сервера. Во время complete показано ожидание подтверждения,
во время publish — ожидание публикации. Ошибка сохраняет форму и тот же File.
Ручной повтор обновляет ссылки для недостающих частей, повторяет нужные операции
по тому же ID, а не создаёт очередной черновик. Неуспешный POST создания не
повторяется автоматически: контракт B08 не имеет ключа идемпотентности.

GET processing опрашивается при незавершённой обработке; фоновых процентов нет.
Показываются реальные состояния качеств, полный/частичный отказ, готовые варианты.
Очередь качества отличается от активной обработки, известные причины полного
отказа переведены в безопасные сообщения. При ошибке чтения прежние качества
и ссылка просмотра скрываются, есть ручной повтор — [F24](upload-processing.md).
После готовности разрешённого
опубликованного видео появляется обычная ссылка `/watch?v=<id>`.
Скрытое/неподготовленное видео не получает обещания доступного просмотра.

## Жизненный цикл и код

- [Страница](../../frontend/src/pages/upload/ui/UploadPage.vue) использует
  отдельную оболочку Studio и сессию; [виджет](../../frontend/src/widgets/video-upload/ui/VideoUpload.vue)
  владеет локальным черновиком формы и Query настроек/обработки.
- [Передача](../../frontend/src/shared/lib/uploads.ts) проверяет размер/границы,
  уникальные номера частей, точные ID и same-origin `/uploads/`. Параллелизм
  берётся из плана API; File.slice не читает весь исходник в память.
- Контрольные операции идут через сгенерированный Hey API и точный JSON-адаптер,
  с cookie/CSRF. XHR не включает cross-origin credentials; Nginx удаляет cookie
  и Authorization перед RustFS. Сами подписанные URL не печатаются и не кэшируются.
- `/studio/upload?video=<id>` восстанавливает данные владельца с сервера.
  Готовая публикация переживает обновление. Незавершённый исходник после потери
  File требует отдельной новой загрузки; автоматическая докачка не обещается.
- Уход/Escape отменяет XHR и запросы, очищает File/форму/кэш прежних Query.
  Поздний ответ не меняет маршрут. После закрытия фокус возвращается на «Создать».
  Tab удерживает фокус в модалке. 401/смена сессии убирают личный интерфейс,
  403/404 убирают метаданные и прекращают операции.

F22 привязывает чтение настроек к ID из query key и исходному владельцу,
проверяет поколение после валидации и до первой команды, снимает неактивные
запросы штатным gcTime 0. Полевая ошибка разблокирует форму перед фокусом;
CSRF отделён от обычного отказа доступа — [проверки и границы](upload-start.md).

Бэкенд не менялся. Типы/SDK обновлены генерацией из OpenAPI работающего dev.
Пользовательские названия, даты, состояния и права не имитируются.

## Проверки

Отдельная приёмка F25 — [upload-publication.mjs](../../docker/browser/upload-publication.mjs):
по 35 проверок Chromium/Firefox, ожидание готовности после публикации,
поздняя публикация, public/private/hidden, неверный ответ/потеря после commit,
повтор без дублей/смены дат, CSRF/401, восстановление и правки метаданных.
Инъекции и границы проверки — [F25](upload-publication.md).

Отдельная приёмка F24 — [upload-processing.mjs](../../docker/browser/upload-processing.mjs):
по 39 проверок Chromium/Firefox, раннее низкое/поздние HD/4K/HDR, полный/частичный
отказ, ошибки чтения/повтор, поздние ответы, настоящие отказы прав/сессии.
Подмена стадий и границы проверки — [F24](upload-processing.md).

Отдельная приёмка F23 — [upload-transfer.mjs](../../docker/browser/upload-transfer.mjs):
по 33 проверки Chromium/Firefox с настоящими multipart-частями, повтором только
недостающей части, ложным ACK, отказами complete/содержимого и потерей сессии.
XHR явно читает пустой ответ как text, без неявного XML-парсинга Firefox.
Материалы, инъекции отказов и границы проверки — [F23](upload-transfer.md).

Актуальная отдельная приёмка F22 — [upload-start.mjs](../../docker/browser/upload-start.mjs):
по 47 проверок Chromium/Firefox, в том числе реальный успешный путь передачи,
публикации и готовности. Она не закрывает полную приёмку F23–F25.
Ранний связанный прогон ниже сохраняет результат первого этапа;
новый профиль не повторяет его скриншоты и геометрические замеры.

В Docker прошли Hey API, vue-tsc/Vite build, ESLint/Prettier затронутых файлов,
Ruff/форматирование fixture и 8 unit-проверок (в том числе два новых сценария
URL/планов передачи). Chromium и Firefox выполнили по **41 профильной проверке**:
гость/возврат ко входу, выбор файла/метаданные, 100/5000 Unicode без обрезания,
явный доступ, ошибки create/PUT/complete/publish, повтор без нового черновика,
реальный скачанный исходник и обработка, public/private после выхода, точные ID,
обновление страницы, защищённый повтор неполной передачи, частичный/полный отказ
по DTO, Escape/Tab/фокус, связь с созданием плейлиста, телефон, уход и 401.
Полный `make check` не запускался: остальные задачи фронтенда ещё впереди.

Профильный браузерный сценарий — [upload.mjs](../../docker/browser/upload.mjs).
API работает на случайной отдельной БД и отдельном префиксе сессий;
[fixture --upload](../../docker/browser/fixture.py) запускает реальный media-worker.
[Runtime](../../docker/browser/upload-runtime.yml) применяет обычные ограничения
медиапроцесса; [Nginx](../../docker/browser/upload-nginx.conf) использует штатный
gateway API/хранилища. Рабочая БД не изменяется; остановка SIGINT прекращает
worker, удаляет созданные исходники/пакеты/превью/сессии и временную БД.

Используется скачанный `portrait.mp4` из [каталога тестовых материалов](watch.md).
Новые аудио/видеоматериалы не генерируются. 503/задержки на этапах create/PUT/
complete/publish и DTO частичного/полного отказа вводит только тестовый HTTP-прокси.
Реальная успешная обработка и изоляция public/private подтверждаются отдельно;
инъекция DTO не выдаётся за фактический отказ кодировщика.

Для повтора нужен dev, образ `youtube-browser-check` и скачанные файлы
`/tmp/frontend-media` по [инструкции материалов](watch.md).
Сначала запустить API/worker в отдельном терминале:

```bash
mkdir -p /tmp/frontend-browser-results
./docker/run dev -f docker/browser/upload-runtime.yml run --rm --no-deps \
  --name youtube-frontend-upload-api \
  --volume "$PWD/docker/browser:/checks:ro" \
  --volume /tmp/frontend-media:/media:ro \
  --volume /tmp/frontend-browser-results:/work \
  python python /checks/fixture.py --upload
```

Затем gateway и нужный браузер (для Firefox добавить `--firefox`):

```bash
./docker/run dev run -d --no-deps --name youtube-frontend-upload-gateway \
  --volume "$PWD/docker/browser/upload-nginx.conf:/etc/nginx/nginx.conf:ro" nginx
docker run --rm --network youtube_default --user "$(id -u):$(id -g)" \
  --volume "$PWD/docker/browser:/checks:ro" \
  --volume /tmp/frontend-media:/media:ro \
  --volume /tmp/frontend-browser-results:/work --workdir /checks \
  youtube-browser-check /checks/upload.mjs
```

После завершения браузеров отправить fixture SIGINT и дождаться сообщения
`Browser fixture: isolated sessions and database removed`, затем убрать gateway:

```bash
docker kill --signal=SIGINT youtube-frontend-upload-api
docker stop youtube-frontend-upload-gateway
docker rm youtube-frontend-upload-gateway
```

Проверки 5 ГБ/планов выполняются по метаданным, без передачи 5 ГБ из браузера.
Границы настоящего конвейера/отказы зависимостей остаются в B09/B10/B18.
Превью, выбор плейлистов и выдача email-доступа в форме подключены —
[код и профильные проверки](video-options.md).
Таблица собственных видео и общий вход в [настройки F26](video-settings.md) подключены;
сведения доступны из обеих таблиц и по ссылке из окна загрузки.
Закрытие загрузки возвращает в список видео, для черновика — с `publication=draft`.
Проверены ширины 390/320, прокрутка формы и достижимость действий.
Для Studio достаточно общего сходства по ADR-0068; точная мобильная копия не требуется.
Safari/WebKit и реальная экранная клавиатура ещё не проверены.
