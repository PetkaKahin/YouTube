# Передача исходника и подтверждение приёма

F23 — `done` по функциональному профилю Chromium/Firefox. Начало формы описано
в [F22](upload-start.md), общий сценарий — в [загрузке Studio](upload.md).
Обработка проверена отдельным [профилем F24](upload-processing.md),
публикация — [профилем F25](upload-publication.md).
Внешний вид проверяет пользователь; снимки и сравнение оформления не выполнялись.

## Байты, подтверждение и повтор

[transferParts](../../frontend/src/shared/lib/uploads.ts) проверяет план API:
точный ID, размер исходника, границы и уникальность частей, same-origin
`/uploads/` без userinfo/fragment. Части создаются File.slice и отправляются
XHR PUT с параллелизмом из плана. Целый File не читается в память приложения.
Ответ PUT явно имеет responseType text: пустой ответ не должен запускать
неявный XML-парсер Firefox. Для результата используется HTTP-статус.

Прогресс складывается из байтов уже принятых частей по refresh и фактически
отправленных байтов текущих XHR. Знаменатель — полный размер исходника.
Клиентские 100% могут появиться до ответа PUT; они не подтверждают приём.
[VideoUpload](../../frontend/src/widgets/video-upload/ui/VideoUpload.vue) отдельно
показывает ожидание complete. Переход к публикации возможен только после
статуса uploaded в ответе complete и повторного чтения настроек с сервера.
Успешный HTTP с неожиданным статусом не считается подтверждением.

При ошибке сохраняются File и ID черновика/передачи. Ручной повтор вызывает
refresh, получает только недостающие части и новые ссылки. Принятая часть
повторно не отправляется; пустой план позволяет повторить только complete.
Автоматического повтора создания, pause/resume и отмены с удалением нет.
Уход прерывает XHR и убирает локальный File; поздний ответ не запускает complete.
Восстановление после потери File и защита контекста описаны в F22.

Клиент проверяет 1..5 000 000 000 байт; фактическое содержимое/длительность
проверяет сервер после приёма. Принятый невидеофайл может завершить передачу
и получить отказ обработки: это не готовое видео, ссылка просмотра отсутствует.
Потеря сессии очищает приватную форму; отказ CSRF оставляет разрешённый черновик
и исходник для явного повтора. XHR не включает cross-origin credentials;
same-origin cookie удаляет Nginx перед RustFS, как и Authorization.

## Проверки

В Docker прошли vue-tsc/Vite build, ESLint/Prettier изменённого uploads.ts,
два unit-сценария URL/планов, синтаксис и форматирование браузерного профиля.
[upload-transfer.mjs](../../docker/browser/upload-transfer.mjs) выполнил
по **33 функциональные проверки** в Chromium и Firefox на ПК и ширине телефона.
Пустые ответы PUT больше не вызывают ошибок XML-парсера Firefox.

Профиль использует настоящие API/PostgreSQL/Valkey/Nginx/RustFS и worker,
отдельную БД и новые аккаунты. Проверены:

- Медленная multipart-передача: реальный скачанный исходник 29 817 869 байт,
  точные части 16 777 216 и 13 040 653 байта, промежуточный процент по байтам.
- Отказ второй части после сохранения первой: нет complete/публикации,
  refresh возвращает только вторую часть, повтор сохраняет прежние ID.
- Отказ complete и повтор с пустым планом без нового PUT; 100% при удержанном
  ответе PUT и ожидание complete без ложного «Сохранено»/просмотра.
- Ложный успешный PUT без записи в RustFS: настоящий complete отвечает 409,
  черновик остаётся непринятым; повтор реально передаёт недостающую часть.
- Разрыв соединения, неожиданный статус complete при HTTP 200, последующий
  повтор без дубля черновика/частей; настоящий успешный приём и публикация.
- Неверный размер плана и внешний URL: нет отправки байтов/внешнего запроса.
  Настоящие 422 для заявленного размера больше 5 ГБ, CSRF 403 и 401 на complete.
- Закрытие во время PUT без позднего complete; настоящий отказ worker для
  скачанного VTT вместо видео и 404 обычного просмотра такого исходника.
- DTO отказа duration_limit после приёма: обработка завершилась ошибкой,
  просмотр недоступен, прогресс передачи не изображается готовностью.

503, обрыв, задержки, ложный ACK PUT, неправильные планы/статус complete
и duration_limit вводит тестовый HTTP-прокси. Отказ по длительности проверяет
реакцию клиента на контракт; видео длиннее часа не генерируется и не передаётся.
Фактическую границу длительности/размера и транзакции хранилища покрывают
[B09](../backend/uploads.md) и [B10](../backend/source-processing.md).
Проверка 422 меняет заявленный размер запроса, без выделения 5 ГБ.
SQL/сбои внутренних зависимостей относятся к серверным тестам; новых парсеров,
пользовательских SQL или HTML-вставок в этом изменении нет. Права, текст формы
и смена аккаунта проверены в F22; здесь дополнительно проверены CSRF/401,
утечки через внешние URL и отсутствие запрещённой публикации после отказа.

## Материалы и повтор

Добавлен готовый multipart.mp4 из Google Shaka в
[каталог с URL/размером/SHA-256](../../docker/browser/media-sources.json).
[Загрузчик](../../docker/browser/download-media.mjs) проверил все семь материалов;
файлы хранятся вне репозитория. Генерации видео/изображений нет.
Малый успешный исходник — portrait.mp4, невидеосодержимое — captions.vtt.

Запуск — по [общему профилю загрузки](upload.md#проверки), но fixture
`--media --links --upload`, браузер `/checks/upload-transfer.mjs`, Firefox —
`--firefox`. Нужны mounts `/checks`, `/work` с manifest и `/media` с материалами;
браузеры запускаются последовательно. SIGINT fixture останавливает worker
и удаляет тестовые объекты, сессии и БД; рабочие данные не затрагиваются.
Диагностика профиля скрывает URL ошибок и не печатает подписанные ссылки/ключи.

Бэкенд, контракт и зависимости не менялись. Safari/WebKit и физический телефон
не квалифицированы; полный make check остаётся до завершения плана.
