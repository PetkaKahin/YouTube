# Служебная модерация

Статус: F30–F32 реализованы. Компоновка согласована пользователем 2026-11-17: пункт «Модерация»
в меню сотрудника, очередь таблицей в стиле Studio, отдельная страница жалобы
с материалом и решениями, одна колонка на телефоне. Референсов внутренней
панели YouTube нет; это проектный интерфейс в согласованном стиле.
Контракт и полномочия — [B33–B36](../backend/moderation.md).

## Маршруты и очередь

`/moderation` показывает ожидающие жалобы старыми первыми по серверному порядку.
Порции по 20 с cursor, автопродолжением и кнопкой; ID дедуплицируются.
Таблица содержит номер жалобы, причину, ID видео/отправителя и дату отправки.
Email, профиль отправителя, фильтры и назначение ролей не добавляются.
На телефоне таблица прокручивается внутри своего контейнера.

Гость получает вход с возвратом, обычный пользователь — отказ без запроса очереди.
Кнопка меню и раздел Studio доступны moderator/admin, но каждый API-запрос
отдельно проверяет актуальную роль. Предусмотрены загрузка, пустая очередь,
ошибки первой/следующей порции и явный повтор.

## Жалоба и служебное видео

`/moderation/<report_id>` читает актуальный контекст, включая ревизию,
и отдельно материал только ожидающей жалобы. Текст явно обозначает служебное
основание просмотра. Название и описание выводятся как текст.
Используется существующий HLS-плеер с готовыми качествами, субтитрами и контролами.
Его необязательный `reportId` формирует строгий префикс
`/api/v1/moderation/reports/<id>/hls/`; обычный просмотр продолжает использовать
`/api/v1/videos/<id>/hls/`. Вложенные запросы не выходят за свой префикс.
Метаданные и постер также проверяются на same-origin и путь текущей жалобы.
Сервер фиксирует основание и исполнителя; постоянное разрешение на видео не создаётся.

## Решения

«Отклонить жалобу» и «Скрыть видео» открывают подтверждение. Для скрытия
обязательна одна из шести готовых причин; свободного текста нет.
PUT отправляет текущую ревизию. Перед записью отменяется загрузка материала,
плеер останавливается на время ожидания: закрытие жалобы на сервере не вызывает
гонку с поздними HLS-запросами. Ожидание блокирует повторную отправку,
ошибка оставляет подтверждение для повтора. 409 закрывает устаревшую форму,
загружает контекст заново и просит проверить данные перед новым решением.
Автоматического повторного решения новой ревизии нет.

Только ответ сервера подтверждает итог, убирает рассмотренную жалобу из
сохранённых порций очереди, удаляет материал из кэша и останавливает плеер.
Завершённая страница показывает текущее решение; повторная подача открывает
новую ревизию по правилам сервера. UI не предлагает снять скрытие, апелляцию,
страйк, блокировку аккаунта или модерацию комментариев.

## Код, доступ и состояние

[ModerationPage](../../frontend/src/pages/moderation/ui/ModerationPage.vue)
владеет Query очереди/контекста/материала и локальным выбором решения.
Ключи `moderation / session.scope / role / resource / revision` изолируют
сотрудника, роль, обращение и его материал. Неактивные данные имеют `gcTime: 0`.
MutationCache не получает поля формы в переменных вызова. Cookie/CSRF и точные
int64 проходят адаптер Hey API, генерация вручную не меняется.

Смена роли/видео/сессии и уход закрывают подтверждение и отменяют операции.
401/403/404 прекращают служебный просмотр, очищают служебный кэш и обновляют
сессию. После ухода удаляются прежние экземпляры Query; поздний ответ не
восстанавливает страницу или сообщение. Отзыв роли обнаруживается при следующей
серверной проверке, включая фокус окна и вложенные запросы HLS; push-канала нет.
Обычные страницы не получают служебные метаданные или ссылки.

## Проверки и ограничения

В Docker прошли vue-tsc/Vite build, ESLint и Prettier затронутого фронтенда,
Ruff/Formatter тестовой fixture. В Chromium и Firefox прошли по **34 профильных проверки**. Проверены реальные
решения, 409 при новой ревизии, 503/повтор/двойное нажатие, служебный HLS
и декодирование приватного материала, отсутствие обычного доступа по одной роли,
живой отзыв роли и очистку кэша, администратора, скрытие в обычном API,
пагинацию, точные ID, клавиатуру, телефон и поздний ответ после ухода.

Профиль — [moderation.mjs](../../docker/browser/moderation.mjs), реальные
изолированные API/PostgreSQL/Nginx/RustFS, готовые медиа и реальные роли/ревизии.
[moderation_seed.py](../../docker/browser/moderation_seed.py) добавляет только
в fixture сотрудников и 42 жалобы через существующие сценарии; ID жалоб больше
2^53. Команды тестовой смены роли/повтора доступны только отдельному API fixture
при `--moderation`, не рабочему приложению. Ошибки 503 и задержка — тестовый прокси.

Запуск — как [профиль загрузки](upload.md#проверки), fixture `--media --moderation`,
в браузерной команде `moderation.mjs`, для Firefox добавить `--firefox`.
Два браузера запускаются последовательно: они меняют те же жалобы и роль fixture.
SIGINT удаляет только тестовую БД, сессии и медиа. Safari/WebKit и реальная
экранная клавиатура не проверены. Полный `make check` остаётся после завершения
итоговой приёмки фронтенда; [панель заданий T12](job-administration.md) подключена отдельно.
