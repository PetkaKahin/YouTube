# Восстановление сессии и доступные действия

F07 — `done` по функциональному профилю Chromium/Firefox. Вход описан в
[F06](login.md), выход — в [F08](logout.md). Отзыв доступа проверен
в [F33](access-lifecycle.md). Внешний вид проверяет пользователь,
снимки и сравнение оформления не выполнялись.

## Личность и проверка

[useSession](../../frontend/src/entities/session/model/session.ts) получает
личность через GET auth/me и Query. До первого ответа показывается проверка
аккаунта, персональные и служебные запросы не запускаются. Валидная серверная
cookie восстанавливает аккаунт после reload; клиент не хранит её значение
в Pinia/localStorage и не рассчитывает срок сессии самостоятельно.

401 auth/me означает подтверждённого гостя. Сетевой/HTTP-сбой либо неверный ID
ответа — отдельная ошибка проверки, а не гостевой успех и не прежняя роль.
В этом состоянии account скрыт, данные зависимых личных Query очищаются, действия
аккаунта и служебная навигация убраны. Повтор получает актуальный ответ и свежие
личные списки. Несколько ручных повторов используют один запрос через
refetch(cancelRefetch=false), без отмены/перезапуска уже выполняющейся проверки.
Query личности может сохранять прежний успешный снимок при ошибке, но account
его не использует и интерфейс не выдаёт его за актуальное подтверждение.

Личность принадлежит Query, account/scope производны от неё. Смена аккаунта,
ошибка личности и expire снимают прежние запросы. Подтверждение входа отменяет
старый запрос личности до установки нового аккаунта. Поздний auth/me прежней
сессии не восстанавливает её после 401 и не заменяет явно вошедшего пользователя.
Back/Forward и отзыв медиа дополнительно проверены в [F33](access-lifecycle.md).

## Роль, права и cookie

Роль берётся из текущего ответа сервера. Moderator получает модерацию,
admin — также историю заданий, user — обычные действия. Прямой URL не даёт
служебного запроса до подтверждения подходящей роли; API проверяет права
независимо от оболочки. Ключи/поколения служебных экранов учитывают роль:
при её снятии убираются данные/действия, поздний старый ответ не возвращает их.
Отказ служебного API перепроверяет личность и снимает устаревшие полномочия.
Роль сотрудника не даёт обычного просмотра чужого private-видео.

Завершённая серверная сессия не оживает по сохранённой cookie. При истечении
или потере записи Valkey требуется новый вход; постоянные данные видео
сохраняются. Изменяющие запросы защищает серверный CSRF; отказ без токена
не завершает действующую сессию. В браузере проверена недоступность session
через document.cookie при реальном авторизованном запросе с этой cookie.
Правила 30 дней, продление и prod-флаги — [B03/B04](../backend/modules/user.md#cookie-и-valkey).

## Проверки

В Docker прошли vue-tsc/Vite build, ESLint/Prettier модели сессии, Ruff и
форматирование fixture с конфигурацией backend/pyproject.toml, синтаксис и
форматирование браузерного сценария.
[session.mjs](../../docker/browser/session.mjs) выполнил по **37 функциональных
проверок** в Chromium и Firefox:

- Гость и reload действующего входа, удержанный auth/me на Studio, загрузке,
  модерации и админ-странице без личных данных/запросов до подтверждения.
- Ошибка фонового auth/me без прежних данных и ложного гостевого состояния,
  клавиатурный повтор, несколько нажатий с одним запросом, возврат свежего
  каталога; отказ от некорректного ID личности.
- Настоящее истечение TTL и удаление записей сессий в Valkey fixture,
  реальный 401 с оставшейся cookie, отсутствие восстановления по клиентскому
  кэшу и новый вход с сохранёнными видео; настоящий CSRF 403 без потери сессии.
- User без служебных ссылок и запросов по прямому URL, реальные 403 обоих API;
  повышение user → moderator → admin в существующей сессии через User.public.
- Снятие роли при открытой истории, поздний разрешённый ранее ответ,
  автоматическое обновление роли после реального отказа API, отсутствие
  обычного доступа к чужому private даже у администратора.
- Поздний auth/me после 401 защищённого запроса и после входа другого аккаунта;
  HttpOnly-cookie, отсутствие password/session в данных аккаунта, отсутствие
  пароля в local stores; телефон, ошибка личности и клавиатурный повтор.

Используются настоящие API/PostgreSQL/Valkey/Nginx/RustFS и изолированная БД.
503, задержки и неверный ID auth/me вводит HTTP-прокси. Роли меняет существующая
тестовая команда User.public; отказы прав, CSRF и сессии не подменяются.
SQL/транзакции и календарную границу 30 дней покрывают B02–B04; новых парсеров
или SQL в реализации клиента нет. Приватность каждого медиамаршрута — B22/F33.

## Повтор и границы fixture

Запуск — как [общий браузерный runtime](upload.md#проверки), fixture
`--media --links --moderation --session` без `--upload`, браузер
`/checks/session.mjs`, Firefox — `--firefox`. Нужны `/checks`, `/work` с manifest
и `/media`; браузеры идут последовательно, новых материалов не генерируется.

Флаг --session добавляет только в [браузерную fixture](../../docker/browser/fixture.py)
POST /__session_fixture/lost и /expired: они удаляют либо устанавливают TTL
1 секунда только ключам её случайного префикса. Контроль вызывается отдельным
гостевым запросом с CSRF, чтобы завершение запроса не продлило проверяемую
сессию. Это проверяет реакцию клиента на реальное отсутствие записи/истечение,
а не ожидание 30 дней или отказ всего сервиса Valkey. Рабочие ключи и настройки
TTL приложения не меняются. Ответ содержит только факт и число записей.
SIGINT fixture удаляет её объекты, сессии и БД; секреты в отчёт не печатаются.

Бэкенд приложения, контракт и библиотеки не менялись. Safari/WebKit и физический
телефон не квалифицированы; общий make check остаётся до завершения плана.
