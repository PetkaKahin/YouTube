# Плейлисты

Реализованы сценарии/API B26–B28 по [ADR-0058](../decisions/0058-playlist-contracts.md),
[правилам Channel](modules/channel.md). Новых библиотек нет.

POST `/api/v1/playlists` создаёт плейлист текущего канала: title/description/visibility.
GET `/api/v1/playlists/mine?cursor=...` — все три режима владельца, новые сначала
по created_at/id. Название 1–100 после trim, описание до 5000, обычный текст;
владелец, даты и служебные поля не принимаются от клиента.

GET `/api/v1/videos/{id}/playlists?cursor=...` возвращает владельцу его плейлисты
с selected для текущего видео. PUT того же пути заменяет полный набор
playlist_ids, включая пустой. Можно выбрать любое число своих плейлистов;
пагинация списка не ограничивает количество выбранных. Нельзя включать чужое
видео или чужой плейлист через этот Studio API. Все изменения — в одной транзакции.
Для R20 реализован [отдельный контракт сохранения доступного видео](watch-save.md),
включая чужое; owner-проверка Studio сохраняется.

GET `/api/v1/playlists/{id}?cursor=...` возвращает доступные метаданные и
страницу видео: public/unlisted — всем, private — только владельцу.
Каждое видео требует независимого опубликованного/готового/нескрытого состояния
и public/owner/email. Недоступные элементы исключаются до заполнения страницы
и определения продолжения, не раскрываются через счётчики или placeholders.
Знание плейлиста/курсора не разрешает медиапути. Успешная пустая страница допустима.

Дополнение Q49: успешный ответ содержит обязательный `channel: {id, name, tag}`
рядом с `playlist`, `items`, `next_cursor`. Это канал владельца плейлиста,
в том числе для пустого public/unlisted и private-плейлиста владельца, а также
страницы продолжения. Профиль читается после проверки прав в той же транзакции:
Channel читает собственный канал, имя получает через User.public.
Канал не восстанавливается по карточкам; email/owner_id не раскрываются.
Отсутствующий профиль даёт общий 404, отказ чтения — общий 500 без частичных
метаданных. Схема БД, списки и ответ создания плейлиста не меняются.

Миграция 0017: channel_playlists и channel_playlist_entries. Уникальная пара
playlist/video, постоянный монотонный ID включения задаёт порядок ASC;
удаление/новое включение получает новый ID. Владелец блокирует сначала своё
видео через Video.public, затем канал для сериализации состава; даты видео
и затронутых плейлистов обновляются только при реальном изменении выбора.
Создание плейлиста не меняет ни одного видео. Удаление/переименование плейлистов
и редактирование их видимости не добавляются: они не запрошены.

Списки/содержимое — по 20, lookahead после фильтра прав. Версионный курсор
содержит границу и назначение/объект/владельца, без медиа/секретов. Он не
предоставляет прав; каждый запрос читает постоянные актуальные данные.
Курсор не фиксирует исторический состав: повторное включение получает новую
позицию и может встретиться при дальнейшем чтении после изменения плейлиста.
Некорректный cursor — общий 422; чужое/отсутствующее — одинаковый 404.
Сессия/CSRF обязательны для изменений. Ответы no-store/Vary Cookie.

Channel владеет составом, Video — проверкой владения/прав и карточками видео.
Адаптеры обращаются через public, без JOIN к чужим таблицам. Получение карточек
пакетное и участвует в транзакции вызывающего сценария. Медиаобъекты не читаются.
Квалификация: public/unlisted/private, приглашённый/владелец/роль/гость,
частичная готовность, отзыв/private/hidden, 20/21 и равные даты, чужие ID,
параллельные/повторные выборы, rollback и сохранение дат/порядка/объектов,
SQL/HTML/Unicode/курсор, отказы PostgreSQL/Valkey и отсутствие утечек.

прошли; контракт подтверждён в OpenAPI работающего dev. Проверки остальных
