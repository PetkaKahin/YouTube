## Ответственность и данные

По R18 реализована [последняя позиция просмотра](../watch-progress.md),
постоянная для аккаунта и отдельная от метаданных публикации.

Реализованы [отдельные списки своих видео и черновиков Q50](../own-videos.md)
для Studio: GetMyVideos и GET `/api/v1/videos/mine`. Интерфейс F26 — отдельный этап.

Реализованы B08, приём файла B09 и B12: создание черновика, чтение настроек
и изменение названия/описания/видимости владельцем. Подробности передачи —
[прямая загрузка](../uploads.md). Публикация,
просмотр и обработка выполняются отдельными сценариями;
разрешения и GET метаданных подключены по [контракту доступа](../private-access.md).
Название обязательно: 1–100 символов после удаления крайних пробелов;
описание необязательное, до 5000 символов, обычный текст с сохранением переносов.
[ADR-0037](../../decisions/0037-video-metadata.md).
Выбор файла, форма метаданных и создание черновика в браузере проверены в
[функциональном профиле F22](../../frontend/upload-start.md); приёмка следующих
этапов загрузки остаётся отдельной.

Схема первого этапа: `video_publications`, bigint ID/owner_id, FK аккаунта,
метаданные и независимые состояния. Начальные значения: публикация draft,
передача pending (ещё не начата), обработка pending, модерация visible;
added_at отсутствует до подтверждения загрузки. created_at/updated_at задаёт БД.
Проверка существующего аккаунта идёт только через User.public; чтение/изменение
ограничены владельцем в сценарии и запросе к БД. Чужой и отсутствующий ID дают
одинаковый 404, роли admin/moderator не заменяют владение. Изменение берёт
блокировку строки; повтор тех же нормализованных значений не меняет updated_at.
Ни один запрос настроек не меняет added_at/публикацию/обработку/скрытие.

HTTP: POST `/api/v1/videos` создаёт черновик (201), GET/PUT
`/api/v1/videos/{id}/settings` читают/заменяют настройки (200). Для POST/PUT
нужна сессия и CSRF, GET требует сессию. PUT передаёт полный набор title,
description, visibility; у POST описание по умолчанию пустое. Владелец берётся
из подтверждённой сессии. Ответы настроек не кэшируются общими кэшами.
Код: [домен](../../../backend/src/video/domain/publications.py),
[сценарии](../../../backend/src/video/application/publications.py),
[репозиторий](../../../backend/src/video/infrastructure/publications.py),
[контроллер](../../../backend/src/app/http/videos.py),
[миграция 0003](../../../backend/migrations/versions/0003_video_publications.py).
VideoActors проверяет аккаунт через User.public.GetAccount в общей транзакции.
CreateDraft/GetVideoSettings/EditVideoSettings экспортируются через Video.public
и доступны через DI вне HTTP с теми же правилами. StartUpload/RefreshUpload/
CompleteUpload/ExpireUploads, InspectSource/RepairSourceProcessing,
PlanMedia/EncodeTrack/RepairEncoding также доступны
через public. GetPrivateAccess/SetPrivateAccess/GetViewableVideo подключают
owner-разрешения (PermissionPage) и доступные метаданные. PublishVideo/GetMedia/GetThumbnailDelivery
подключают публикацию, плейлисты и передачу байтов через Nginx. GetFeed возвращает
публичные готовые карточки и курсор. GetSearch объединяет видео, каналы и плейлисты;
фильтры применяются до заполнения страницы. GetPlaylistVideoCards пакетно
проверяет обычные права элементов плейлиста; PlaylistVideoOwnership участвует
в транзакции Channel для проверки владения и обновления даты реальной правки.
GetChannelFeed возвращает публичные карточки конкретного канала.
GetVideoLike/SetVideoLike возвращают счётчик и собственное состояние, проверяя
обычный доступ; запись пары сериализуется с изменением видимости/разрешений.
RequireDiscussionVideo участвует в транзакции Comment: удерживает разделяемую
блокировку публикации и разрешает обсуждение только при обычном доступе к public.
Контракт — [комментарии](../comments.md).
ReportVideoAccess подключает внутренние команды скрытия и чтения материала
для оркестратора Moderation; он проверяет ожидающую жалобу и сохраняет
основание/исполнителя. Обычный просмотр не получает исключения по роли —
[контракт модерации](../moderation.md).

Владелец, название, описание, превью, видимость, разрешённые зрители, состояние
публикации/обработки/скрытия, исходник, варианты HLS и лайки. Постоянное состояние
в PostgreSQL, файлы в RustFS. Идентификатор владельца не меняется по вводу клиента.

По запросу пользователя совпадение исходников проверяется доверенным серверным
хешем до обработки; совместимые готовые результаты переиспользуются.
Оригинал хранится временно для слепка и перекодирования по
[ADR-0040](../../decisions/0040-temporary-originals.md). Готовые видеоварианты —
только AV1 по [ADR-0039](../../decisions/0039-av1-encoding.md).
Клиентский хеш не открывает доступ к уже существующему объекту.
Логические видео сохраняют независимые метаданные и права.
Дедупликация глобальная для всех аккаунтов, включая совместимые HLS и превью.
Общие готовые результаты сохраняются до освобождения всех пользовательских ссылок.
У каждой публикации собственные медиассылки с проверкой её прав.
Слепки содержимого дорожек без описательных тегов проверяются до конвертации;
подтверждённый дубль повторно не кодируется. Выбраны сжатые данные дорожек
с точным таймингом и значимыми техническими параметрами, без полного декодирования.
Описательные теги файла не сохраняются в постоянных медиа; технические метаданные
сохраняются. Итоговый digest — SHA-256, для очереди выбрана Procrastinate —
[ADR-0034](../../decisions/0034-sha256-and-procrastinate.md).

## Видимость и доступ

Только два режима: `public` и `private`.

| Сценарий | Публичное готовое видео | Приватное готовое видео |
| --- | --- | --- |
| Просмотр гостем | Да | Нет |
| Просмотр владельцем | Да | Да |
| Просмотр другим пользователем | Да | Только с разрешением владельца |
| Главная, поиск, публичный список канала | Да | Нет |
| Доступ по известному URL без разрешения | Да | Нет |
| Комментарии | Доступны | Недоступны |

Правила публичной выдачи и отключения комментариев у приватного видео взяты из
[справки YouTube](https://support.google.com/youtube/answer/157177?hl=en),
проверенной 2026-11-11. Применяется только часть про public/private.

## Разрешения по email

Утверждено пользователем 2026-11-12; [ADR-0009](../../decisions/0009-private-access-by-email.md).

- Владелец добавляет разрешённые адреса по **email**. Принимается любой корректный
  по формату адрес, независимо от наличия аккаунта в проекте.
- Разрешение адресовано email и может существовать до регистрации получателя.
  Добавление не требует существующего аккаунта или его внутреннего ID.
- В UI и API одинаковый результат для зарегистрированного и ещё не
  зарегистрированного адреса. Нельзя показывать «пользователь не найден», наличие
  аккаунта, его имя, тег, аватар или внутренний ID по введённому адресу.
- Список разрешений показывает введённые владельцем email без статуса регистрации.
  Публичный поиск аккаунтов по этому адресу для формы доступа не нужен.
- Email нормализуется по тем же правилам, что при входе. Повторное добавление
  того же адреса не создаёт дублирующее разрешение.
- Гостевой доступ этим правилом не вводится: для просмотра получатель входит
  в аккаунт. Для учебного проекта доверяем email, указанному при регистрации:
  совпадения нормализованного адреса аккаунта с разрешённым email достаточно
  для проверки получателя. Подтверждение владения почтой не требуется.
  Это согласованный ответ на Q13; остальные проверки готовности, видимости
  и модерации продолжают действовать.

## Применение доступа

- Подписка, лайк и возможность открыть плейлист не дают права приватного просмотра
  содержащегося в нём видео. Разрешение на приватное видео выдаётся отдельно;
  его добавление в плейлист не меняет видимость и список разрешённых email.
  Доступ по ссылке (`unlisted`) предусмотрен только для плейлистов;
  режимы самого видео по-прежнему `public` и `private`.
- Владелец управляет метаданными, видимостью и разрешениями при загрузке
  и в согласованных настройках видео в ЛК. Там же выбираются плейлисты;
  связями «плейлист, видео» владеет [Channel](channel.md).
- Недоступному зрителю не выдаются название, превью, списки качеств или ссылки
  приватного видео через API, поиск, плейлисты, кэш и медиараздачу.
- Проверка чтения учитывает одновременно разрешение, готовность и скрытие.
  Модерационное скрытие запрещает обычное воспроизведение, в том числе владельцу.
  Просмотр для рассмотрения жалобы — отдельное привилегированное действие.
- Переход в `private` и отзыв разрешения закрывают последующие запросы к данным
  и HLS. Уже полученные байты отозвать невозможно; детали медиапроверки — в конвейере.

## Главная и поиск

В выдачу попадают только публичные опубликованные нескрытые видео с готовым
качеством. Главная показывает превью и основные данные карточки.
Утверждено пользователем 2026-11-12; [ADR-0012](../../decisions/0012-feed-and-search-order.md):

- Главная на начальном этапе упорядочена по дате добавления, новые сначала,
  без алгоритма персональных рекомендаций.
- Дата добавления видео — момент успешного завершения загрузки исходника.
  Последующая публикация и готовность качеств не меняют её. Q15 закрыт.
- Поиск видео работает по части названия без учёта регистра; описание
  и содержимое видео не участвуют в совпадении.
- Общий поиск теперь включает также каналы и плейлисты, фильтры по типу,
  длительности, дате загрузки и особенностям, сортировки по созданию/изменению.
  Канонические правила — [поиск](../../project/search.md); бизнес-часть согласована.

Для главной выбрана cursor-пагинация по 20 —
[ADR-0056](../../decisions/0056-feed-cursor-pagination.md).
Для поиска приняты 1–100 символов и cursor по 20 —
[ADR-0057](../../decisions/0057-simple-search.md).
Фильтр доступа применяется до пагинации, подсчёта результатов и отдачи из кэша.
Выбор сортировки не открывает доступ к скрытым или приватным видео.

## Лайки и дизлайки

Вошедший зритель с доступом может поставить один лайк видео и отменить его.
Уникальность пары «пользователь, видео» сохраняется при конкурирующих запросах;
повтор команды установить/снять лайк не меняет результат повторно.
Клиент отправляет целевое состояние, а не ненадёжную серверную команду toggle.
Счётчик и собственное состояние возвращает сервер.
GET/PUT подключены — [контракт и проверки](../video-likes.md).
R21 добавляет личный дизлайк и PUT dislike: выборы взаимоисключаются,
публичного счётчика дизлайков нет. Обычные права сохраняются —
[реализация и проверка](../video-dislikes.md).
Ориентир отмены выбора — [справка YouTube](https://support.google.com/youtube/answer/6083270?hl=en),
проверена 2026-11-11. Остальные функции этой страницы не входят в проект.

## Публичные контракты и проверки

В `Video.public` реализованы GetViewableVideo, owner-разрешения по email,
GetChannelFeed и GetVideoLike/SetVideoLike.
Планируются проверка комментирования и модерационное скрытие.
Сценарий скрытия требует подтверждённой роли, причина и инициатор сохраняются.
Проверки: матрица видимости, утечки через выдачу/превью/HLS, отзыв доступа,
конкурентные лайки и все варианты состояний конвейера.
Для разрешений проверяются сохранение email до регистрации адресата, одинаковый
публичный результат при наличии/отсутствии аккаунта и отсутствие раскрытия
его данных. Вошедший пользователь с разрешённым email получает доступ без
подтверждения почты; другой email и гость доступа не получают.
Для каталога проверяются порядок по дате добавления на главной и в поиске,
поиск по части названия без учёта регистра, сохранение фильтра прав при смене
сортировки, неизменность даты добавления при поздней публикации и обработке.
Проверяется также, что дата изменения обновляется при правках владельца,
но не при просмотрах, лайках или фоновой обработке. Признаки HD/4K/HDR появляются
только после готовности доступных зрителю версий; подходящий исходник не заменяет
готовый результат. Сочетание 4K + HDR требует готового варианта 2160p HDR.
