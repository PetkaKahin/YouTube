# Ресурсы медиаворкера

Подход принят в [ADR-0050](../decisions/0050-worker-resource-configuration.md),
параллелизм/повторы — в [ADR-0035](../decisions/0035-worker-policy-and-job-errors.md).
Численные пределы приняты в [ADR-0051](../decisions/0051-media-resource-limits.md).
На этом этапе реализуем контроль медиапроцесса; постоянные задания, БД, бизнес-логика,
API и действующий upload-maintenance не меняются.

## Найденные ограничения

- На доступном Linux/amd64 Docker-хосте — 16 CPU, около 32 ГиБ RAM, cgroup v2.
  В контейнере `--cpus 2` affinity/`os.cpu_count()`/`os.process_cpu_count()`
  всё ещё показывают 16. `cpu.max` содержит `200000 100000`, то есть 2 CPU.
  Значит, число доступных CPU нельзя брать только из Python CPU count.
- В SVT-AV1 2.3.0 параметр `lp` — уровень параллелизма 0–6, а не число
  потоков. Значение 0 выбирается по ядрам машины; уровни меняют одновременно
  количество потоков и буферов кадров. При CRF уровни 4+ дополнительно
  увеличивают число mini-GOP в обработке и расход памяти.
  Существующие пробы `lp=2` не доказывают ограничение ровно двумя потоками.
- CPU квота ограничивает суммарное процессорное время. Для FFmpeg-фильтров
  и Mesa выбирается соответствующий размер пулов, SVT требует отдельной
  проверенной настройки параллелизма. Это не меняет preset/CRF/tune.

## Методика замеров

Короткие искусственные исходники генерируются в удаляемом контейнере,
без сети/GPU, от app, с cap-drop/no-new-privileges. Preset 6, CRF 28,
tune=0, 60 FPS; проверяются HD/4K и CPU-преобразование синтетического HDR
через libplacebo/Lavapipe BT.2390. Число кадров должно задействовать очередь
кодировщика; это не двухкадровая проверка наличия инструмента.

Для отдельной пробы используются собственные ограничения времени/потоков
и Docker RAM. Они не становятся production-настройками. Сохраняются время,
CPU time, максимальный RSS дочернего FFmpeg, cgroup memory peak, размер
результата, интервалы выдачи прогресса и результат проверки декодирования.
Замеры запускаются последовательно, чтобы не конкурировать между собой.

Синтетическая короткая сцена не доказывает скорость часового видео,
качество разных типов содержимого, верхнюю границу RAM или максимальный
размер вывода при CRF без потолка. Полный объём временного диска должен
учитывать оригинал до 5 ГБ, один текущий результат и незавершённые записи;
потолок диска требует отдельного согласования и проверки остановки.

## Результаты квалификации 2026-11-13

Добавлен отдельный [benchmark_media.py](../../docker/python/benchmark_media.py).
Он не включён в обычный `docker/run check`: это дорогая ограниченная проба,
а не обязательный бенчмарк каждого изменения. Использован уже собранный
prod-образ с зависимостями ADR-0046. Процессы непривилегированные, сеть/GPU
отсутствуют, Docker CPU=2 (также отдельная пара при CPU=1), memory=8g,
memory-swap=8g (без дополнительного swap).
Все пробы последовательные: 96 кадров, 60 FPS, то есть 1,6 с исходной шкалы.
Уровни SVT 1/2 сравниваются с одинаковыми preset/CRF/tune.

[Полные численные результаты](media-resource-samples.json) сохраняют wall/CPU time,
RSS, cgroup peak, наблюдаемое число потоков, прогресс, bytes, exit code и OOM events.

Для SDR `lp=2` уменьшил wall time примерно на 36–39% при росте RSS на 23–25%
и CPU time на 12–16%; это полезный стартовый компромисс при квоте 2 CPU.
При 1 CPU уровень 2 оказался на 31% медленнее уровня 1 и использовал больше
памяти/CPU time. Значит, одинаковый уровень для любого CPU-бюджета не подходит.
Равный размер SDR-результатов не является проверкой визуального качества
или доказательством побитовой идентичности. HDR → SDR существенно дороже;
здоровая обработка до первого положительного `out_time_us` занимала около
157–159 с. Короткий watchdog без учёта этого дал бы ложный отказ.

RSS и cgroup peak — разные показатели: cgroup учитывает также Python,
кэш страниц и память остальных процессов; общие страницы могут учитываться
по-разному. Показатели сняты после кодирования, до контрольного декодирования.
Источник lavfi не измеряет память декодера реального загруженного файла.
Полная длительность, разные сцены/кодеки входа, 8K-вход и arm64 не проверены;
скорость часового видео и верхняя граница памяти этими цифрами не доказаны.

### Проверки ограничения и отказов

- Docker cgroup v2: квоты 0,5/1,5/2 CPU прочитаны как 1/2, 3/2 и 2;
  Python count и affinity оставались 16. С `--cpus 2 --cpuset-cpus 0`
  affinity ограничена одним CPU; учитывать нужно оба вида ограничений.
- Принудительный deadline 1 с для 1080p: процессная группа остановлена
  SIGKILL после 5 с ожидания SIGTERM, всего 6,094 с; OOM events = 0.
- При 256 МиБ и memory-swap=256m FFmpeg получил SIGKILL, cgroup peak=256 МиБ,
  `oom_kill=1`, deadline не срабатывал. Причина отличается от убийства таймаутом.
- Все временные контейнеры завершены, файловые результаты удалены.
  Проверки не затрагивали RustFS, PostgreSQL, исходники загрузок или чужие контейнеры.

Пример фактически выполненной команды для проверочного образа:

```bash
docker run --rm -i --network none --cpus 2 --memory 8g --memory-swap 8g \
  --cap-drop ALL --security-opt no-new-privileges youtube-media-prod:validation \
  python - --case 2160-hdr-sdr --lp 2 --frames 96 < docker/python/benchmark_media.py
```

Обычная проба имеет собственный deadline 240 с; `--timeout-seconds 1` служит
проверке остановки. Код/формат проверены Ruff; полный pytest/HTTP smoke не
запускался: бизнес-код и контракты не менялись. Автоопределение CPU для настоящего
worker, runtime cgroup v1, production-ограничитель диска и восстановление задания не реализованы
этим измерительным скриптом. Позднее пределы приняты в ADR-0051;
инфраструктурный контроль описан ниже.

## Начальные пределы — принято 2026-11-14

Числа ниже приняты после квалификации, изменяются несекретной конфигурацией.
Короткая проба не
гарантирует прохождение любого разрешённого исходника в этих пределах.

| Параметр | Начальное предложение |
| --- | --- |
| CPU-квота контейнера | 2 CPU; размеры пулов по фактической quota/affinity/cpuset |
| RAM всего worker | 8 ГиБ, без дополнительного swap |
| Временный каталог worker | Порог остановки 32 ГиБ, включая локальный исходник и текущие результаты |
| Свободное место на его разделе | Оставлять минимум 2 ГиБ; проверять перед работой и во время неё |
| Нет продвижения обработки | 30 минут до ошибки; важны изменяющиеся позиции/байты, а не просто получение строк progress |
| Общая длительность одной попытки | 7 суток; для длинного HDR/слабой CPU-квоты может потребоваться изменение конфигурации |

Для SVT принят уровень 1 при одном целом доступном CPU, уровень 2
от двух; используются целая часть эффективного CPU-бюджета, минимум 1.
Уровень 0 не должен автоматически выделять ресурсы по 16 CPU хоста при квоте 2.
Preset/CRF/tune/качество этим не меняются; уровни 4+ без дополнительных замеров
не предлагаются. Это начальный консервативный выбор, а не доказанный оптимум
для всех CPU и дробных квот.

CPU/RAM ограничиваются Docker, дисковый порог — контролем рабочего каталога
и свободного места раз в секунду: это не жёсткая файловая quota и возможно
превышение между проверками. Без отдельного согласования не вводим зависимость
от XFS/project quotas или привилегированных монтирований. Для файлов используется
дисковый том, не tmpfs, который расходовал бы тот же лимит RAM.

При распознанном превышении лимита останавливаем только текущую работу:
SIGTERM группе процесса, ожидание 5 с, затем SIGKILL, причина в постоянный журнал.
Неполные результаты не объявляем готовыми, готовые варианты и оригинал сохраняем
по существующим правилам. Распознанный фиксированный ресурсный лимит не имеет
смысла автоматически повторять с тем же бюджетом; временные I/O-сбои и потеря
worker сохраняют политику ADR-0035. Контроль subprocess реализован отдельно
и подключён к постоянному заданию первичной проверки исходника и его журналу —
[границы этапа](source-processing.md).

## Контроль процесса — этап 2026-11-14

Реализованы [конфигурация и cgroup CPU](../../backend/src/video/infrastructure/media_resources.py)
и [адаптер subprocess](../../backend/src/video/infrastructure/media_process.py).
`MediaLimits.from_environment()` читает четыре `MEDIA_*` значения из
несекретной конфигурации; нули/отрицательные/некорректные значения дают безопасную
ошибку. CPU учитывает `sched_getaffinity`, quota своего cgroup и видимых
родителей: v2 cpu.max и v1 cfs. Скрытые namespace предки остаются под контролем
ядра, но их невидимые квоты нельзя использовать для точного размера пулов.

Адаптер получает только серверные executable/argv, запускает без shell
в новой процессной группе. Входные/готовые файлы не удаляются и не публикуются.
Рабочий каталог проверяется перед запуском, во время работы и после даже
быстрого успешного выхода; sparse-файлы считаются по логическому размеру,
symlink/FIFO/device entries не допускаются. Исчезновение файла при штатном
rename сегмента не считается ошибкой. Это не механизм исполнения недоверенной
команды: произвольный argv от пользователя не должен попадать в адаптер.

Оба pipe непрерывно читаются ограниченными порциями. Stderr отбрасывается,
в сообщение ошибки не попадают пути, исходный текст, argv или значения env.
Часы idle обновляются только при росте frame/out_time_us/total_size;
повторяющиеся progress/нули/строки логов их не продлевают. Процессная группа
останавливается и при отмене async-задачи, включая отмену во время spawn
и потомков, переживших завершение родителя. SIGTERM → 5 с → SIGKILL.

Возвращаются стабильные коды `workspace_limit`, `disk_reserve`,
`progress_timeout`, `attempt_timeout`, `memory_limit`, `media_exit_failed`
и безопасные коды ошибок конфигурации/запуска. Превышение RAM распознаётся
по приросту cgroup OOM-счётчика; если погиб весь worker, recovery очереди
фиксирует потерю worker и решает повтор по ADR-0035. `retryable=False` для распознанных
ресурсных пределов; временный I/O/запуск и общий отказ процесса остаются
классифицируемыми вызывающим сценарием. Записи конкретного задания в PostgreSQL
этот адаптер пока не создаёт; инфраструктурный код не подменяет бизнес-решение.

### Изолированная конфигурация Docker

Добавлен [docker-compose.media.yml](../../docker-compose.media.yml):
`media-tools` — проверочный сервис без сети, GPU, секретов, очереди и соседних
сервисов. Он наследует общую политику
[docker/media-runtime.yml](../../docker/media-runtime.yml): 2 CPU, 8g RAM,
8g memory+swap (дополнительного swap нет), дисковый `media_scratch`, app,
cap-drop ALL, no-new-privileges. API и upload-maintenance эту политику не получают.
Ту же политику использует постоянный `media-worker` первичной проверки исходника;
у него дополнительно есть сеть и доступ к PostgreSQL/RustFS.

Новый `./docker/run media ...` запускает эту конфигурацию. Если локального `.env`
нет, используется `.env.example`; init/создание secret-файлов для этой проверки
не требуется. Значения `MEDIA_CPUS`, `MEDIA_MEMORY`, `MEDIA_WORKSPACE_BYTES`,
`MEDIA_RESERVE_BYTES`, `MEDIA_IDLE_SECONDS`, `MEDIA_ATTEMPT_SECONDS` описаны
в [.env.example](../../.env.example). `MEDIA_BUILD_TARGET=dev` позволяет собрать
проверочный dev из того же Dockerfile; по умолчанию prod, оба наследуют base.

```bash
./docker/run media build
./docker/run media run --rm -T media-tools python - < docker/python/check_media_resources.py
```

Проверка с реальным FFmpeg включена в `docker/run check` через отдельный
контейнер с этими ограничениями, а не через неограниченный API exec.
Полный тяжёлый worker и B10/B13–B19 ещё не объявлены готовыми.

### Результаты проверки контроля процесса

В Docker прошли 38 проверок
[test_media_resources.py](../../backend/src/video/tests/test_media_resources.py).
Вместе с HLS, субтитрами и метаданными Video — 161 тест, без ошибок.
Проверены quota/affinity и предки v1/v2 (фикстуры), дробные квоты,
namespace roots/escaped mount paths, отказ при повреждённой quota;
точные границы диска/резерва, sparse-файлы, symlink, отказ до spawn,
рост/финальный размер файла, log flood без newline, отсутствие утечки stderr,
shell-метасимволы как данные. Idle/attempt timeout, SIGTERM-игнорирующий процесс,
внук с открытыми pipe, обычное завершение родителя, отмена во время spawn
и повторная отмена при остановке не оставляют живых процессов.
Оригинал и готовый файл остаются побайтово неизменными.

Финальный код собран и проверен через `docker/run media` в dev и prod:
12 AV1 кадров через preset 6/CRF28/tune0, декодирование, CPU=2,
memory.max=8589934592, memory.swap.max=0; сеть/GPU/secrets отсутствуют.
Prod дополнительно прошёл с MEDIA_CPUS=1.5: определён бюджет 3/2,
пул 1, SVT level 1. В отдельном контейнере MEDIA_MEMORY=256m реальный OOM
дочернего процесса распознан как `memory_limit`, исходник/готовый файл целы.
После запуска временных контейнеров не осталось; том проверки сохраняется,
её временные каталоги удалены самой проверкой.

Ruff/Formatter (130 файлов с проверочными скриптами), Basedpyright,
Tach check/check-external и `bash -n docker/run` прошли. Compose media config
валиден; оба образа наследуют base. Проверка `media-tools` успешно выполняется
без `.env`/secret-файлов с fallback `.env.example`.
Полный `docker/run check`, HTTP smoke и интеграции PostgreSQL/RustFS/очереди
не запускались: они не менялись. Реальная cgroup v1 и arm64 не запускались;
v1 покрыта разбором фикстур. Часовые исходники и production recovery остаются
будущей приёмкой конвейера, короткая проба не является гарантией любого входа.

По безопасности здесь нет новой авторизации, сессий, SQL или браузерного
ввода. Проверены применимые subprocess/path/injection/лимиты/отказы и сохранность
существующих файлов. Дисковый контроль программный: ни эта проверка, ни
Compose не создают жёсткую filesystem quota.

## Источники

Проверены 2026-11-13:

- [Docker resource constraints](https://docs.docker.com/engine/containers/resource_constraints/): CPU quota, RAM и swap.
- [Linux cgroup v2](https://docs.kernel.org/admin-guide/cgroup-v2.html): cpu.max, memory.max/peak, иерархия ограничений.
- [SVT-AV1 2.3.0 Parameters, Appendix A.1](https://raw.githubusercontent.com/AOMediaCodec/SVT-AV1/v2.3.0/Docs/Parameters.md): lp — уровень, а не число CPU/потоков.
- [FFmpeg 7.1.5 libsvtav1](https://raw.githubusercontent.com/FFmpeg/FFmpeg/n7.1.5/libavcodec/libsvtav1.c): настройки кодировщика.
