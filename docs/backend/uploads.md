# Прямая загрузка исходного файла

Статус: B09 реализован и проверен; параметры согласованы в
[ADR-0038](../decisions/0038-multipart-upload-policy.md).

## Контракт и ответственность

POST `/api/v1/videos/{id}/upload` с `size` начинает или возобновляет загрузку;
ответ содержит bigint ID загрузки, статус, размер части, параллелизм,
expires_at и подписанные URL для недостающих частей. POST
`/api/v1/videos/{id}/upload/{upload_id}/refresh` обновляет ссылки;
POST `.../complete` подтверждает передачу. Все операции требуют сессии,
владения публикацией и CSRF, ответы — no-store. Клиент не задаёт bucket,
ключ объекта, ID multipart, ETag, дату или фактический результат проверки.

Размер — целое 1..5 000 000 000 байт. Повтор начала с тем же размером возвращает
действующую загрузку, другой размер отклоняется до истечения/сбоя предыдущей.
После подтверждения исходник не заменяется. Создание, выдача новых ссылок
и успешное подтверждение обновляют серверную активность; передача частей
учитывается по LastModified частей RustFS. Истечение URL не отменяет загрузку.

`video_uploads` хранит самостоятельные попытки передачи, технический ключ
и multipart ID. Создание намерения коммитится до выделения multipart в RustFS;
повтор ищет незавершённую передачу по точному серверному ключу и восстанавливает
связь после потери ответа/commit. Загруженный объект проверяется по HEAD;
при повторе Complete сохраняются дата и один результат. Валидный исходник
остаётся закрытым. Вместе с подтверждением атомарно создаётся задание первичной
проверки: pending → processing, при окончательной ошибке failed. Inspected
не открывает просмотр; [приём в обработку](source-processing.md), B10/B13 частично.
Подключены [слепки](track-fingerprints.md), [готовые дорожки](encoding.md)
и [готовность владельца](readiness.md); зрительская выдача ещё впереди.
Метаданные/приватность/публикация/скрытие не меняются передачей файла.

## Очистка и безопасность

Очистка повторяема и использует те же блокировки публикации/загрузки.
Незавершённые попытки старше 24 часов без API/объектной активности прекращаются,
их временные объекты удаляются; метаданные черновика и история ошибок остаются.
При неясном результате обращения к RustFS удаление/успех не выдумываются.
Работа возобновляется после восстановления зависимости. Старый upload_id
не позволяет завершить новую попытку.

Отдельный same-origin путь `/uploads/` пропускает только PUT в RustFS,
не предоставляет чтение исходников/списков и не передаёт cookie приложения.
S3-подпись ограничивает ключ, uploadId, номер и размер части; значения подписи
не попадают в журналы. Обработчик API не принимает URL для fetch (SSRF).
Проверки: реальные multipart/подписи RustFS, ошибки/неполные части, повтор
Complete после потери commit, конкуренция/очистка, чужое владение, инъекции,
подмена размера/ключа, утечки, границы и истечение URL.

## Код и эксплуатация

[S3-адаптер](../../backend/src/video/infrastructure/multipart.py),
[репозиторий](../../backend/src/video/infrastructure/uploads.py),

Миграция также устанавливает закреплённую схему Procrastinate 3.11.0;
ею владеет библиотека, Alembic не пытается удалить её таблицы по ORM metadata.
Downgrade сохраняет служебную схему/историю очереди.

Сервис `upload-maintenance` использует тот же Python-образ и Compose Secrets,
отдельную очередь maintenance, cron раз в минуту. За один проход выбирает
до 100 просроченных попыток — служебный batch, не ограничение числа видео.
Heartbeat 10 секунд, признание потери после 60 секунд, recovery/перенос
буфера каждые 15 секунд. Три запуска, задержки 30/120 секунд, concurrency=1.
Потеря worker записывается без выдуманного traceback; конкурентные recovery
сериализуются блокировкой записи очереди и не расходуют попытку дважды.
Журнал и middleware — [диагностика](background-jobs.md).
Это worker обслуживания загрузок и восстановления обеих очередей. Первичная
проверка исходника вынесена в отдельный [media-worker](source-processing.md);
транскодирование вариантов подключено к постоянным AV1/AAC-заданиям.

Обновление ссылок возвращает только недостающие/неверно переданные части.
В браузере можно отправлять Blob от File.slice() методом PUT; размер тела
задаёт транспорт, вручную выставлять запрещённый браузером Content-Length
не требуется. LastModified частей берётся из RustFS, не из body клиента.
Активная передача препятствует очистке. При сбое abort до commit очистка
может повториться; исчезнувший multipart не считается успешной загрузкой.

Проверено на реальных сервисах: часть 16 МиБ и остаток, 5 ГБ на этапе плана
(299 ссылок, без передачи 5 ГБ в тесте), подмена размера/номера/ключа, истечение
подписи, перевыпуск, конкурентные start/complete, отказ хранилища, потеря commit
после Create/Complete, очистка и её повтор после сбоя, активные части и готовый
исходник при очистке, неверные размеры частей и готового объекта, права/CSRF,
SIGKILL worker и восстановление/окончательный отказ по бюджету попыток.
Тестовые объекты удаляются, БД изолированы. Защита просмотра и достоверность
видеодорожек/длительности не объявляются реализованными этим этапом.
Полный `make test`: 479 passed (248,40 с). После уточнения стабильного ID
наблюдения потери worker три проверки worker повторно прошли, включая
сбой после сохранения ошибки и очистку строки worker библиотекой.
В dev подтверждено успешное выполнение периодической задачи обслуживания.
Сборки dev/prod, DI, Ruff/Formatter, Basedpyright, оба Tach, uv audit,
`alembic check`, HTTP smoke и `nginx -t` прошли. `make audit`: 8 контейнеров,
50 поверхностей, утечек и непрочитанных argv/environment не обнаружено.
Проверены 91 Markdown-файл и 745 локальных ссылок, `git diff --check` чистый.

Порядок реализации: документы → миграция → домен/сценарии → адаптеры/worker →
HTTP → тесты. Параметры кодирования Q03 и защищённая раздача Q05 до B22
не блокируют передачу исходника.
