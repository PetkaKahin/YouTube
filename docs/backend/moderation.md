# Жалобы и служебная модерация B32–B36

Статус: B32–B36 и ресурсная часть B05 реализованы и проверены. Правила —
[Moderation](modules/moderation.md), приёмка — [задачи](../tasks/backend/moderation.md).
Порядок очереди и готовые причины — [ADR-0061](../decisions/0061-moderation-queue-and-reasons.md).

## Контракт HTTP

- `POST /api/v1/videos/{video_id}/reports`: `{reason}`, вход и CSRF;
  ответ 202 `{accepted: true}` без ID жалобы, отправителя, состояния решения
  или счётчиков. Каждая отправка обновляет время/причину и ревизию единственной
  записи пары «аккаунт, видео»; автоматического скрытия нет.
- `GET /api/v1/moderation/reports?cursor=...`: только moderator/admin,
  ожидающие жалобы по `submitted_at ASC, id ASC`, до 20 за запрос.
  Повтор обновляет время и переносит обращение к новым. Дополнительных
  фильтров нет. Курсор — граница порядка, не снимок очереди.
- `GET /api/v1/moderation/reports/{report_id}`: текущая жалоба и решение
  только её текущей ревизии. Служебный ответ содержит ID отправителя,
  видео, причину, время, ревизию и состояние; email и credentials не возвращаются.
- `PUT /api/v1/moderation/reports/{report_id}/decision`:
  `{revision, action: dismiss|hide, reason?: ...}`, вход сотрудника и CSRF.
  Для hide обязательна готовая причина. Для dismiss отдельная причина не нужна:
  основанием остаётся рассматриваемая жалоба. Повтор одинакового решения
  текущей ревизии возвращает существующее, не меняя исполнителя/время;
  другая команда по завершённой или устаревшей ревизии — 409.
- `GET /api/v1/moderation/reports/{report_id}/video`: метаданные материала
  ожидающей жалобы. Отдельные GET/HEAD `.../preview.webp`, `.../hls/master.m3u8`
  и `.../hls/tracks/{track}/{filename}` обслуживают тот же материал.
  Каждый запрос заново проверяет роль и ожидающую жалобу и сохраняет
  исполнителя, ревизию, причину и вид служебного чтения.

Значения reason: `spam`, `harassment`, `violence`, `sexual_content`,
`copyright`, `other`. Автор определяется сессией; присланные user/role/owner
не меняют субъект или права. Строгая валидация/RFC 9457 и неизвестные поля
следуют общему контракту. Нет сессии — 401, обычная роль на служебном пути —
403, отсутствующий/недоступный объект — 404, неверный ввод — 422.
Ответы используют `no-store`, `Vary: Cookie`; ошибки не отражают входные значения.

Обычный просмотр не получает служебное исключение. К материалу жалобы можно
обратиться только через её ID и актуальную серверную проверку. Готовые HLS,
превью и WebVTT сохраняют относительные пути внутри служебного маршрута;
каждый вложенный запрос снова авторизуется. Прямой RustFS URL не выдаётся,
байты передаёт Nginx по существующему internal-пути. Завершённая жалоба
не открывает служебный просмотр; решение и прежние служебные чтения сохраняются.

## Хранение, транзакции и границы

Миграция 0023 создаёт таблицы Moderation: жалобы с уникальной парой,
решения по ревизиям и записи служебного доступа. Прежние решения сохраняются,
но после повторной отправки не считаются решением нового обращения.
Video уже владеет состоянием `hidden`; отдельная схема видео не нужна.
User добавляет узкое чтение доверенной роли с разделяемой блокировкой аккаунта;
Casbin проверяет серверную роль. Оно участвует в транзакции вызывающего сценария.
Контракт — User.public.GetStaffIdentity; возвращает только ID и роль.

Порядок блокировок: роль сотрудника → публикация Video → запись жалобы.
После ожидания блокировки данные читаются заново. Отправка обычной жалобы
проверяет обычный просмотр, включая разрешённое private, под блокировкой Video.
Служебный сценарий проверяет основание в Moderation; внутренние команды
Video.public читают/меняют собственный материал в той же транзакции.
SQL/JOIN к чужим таблицам не добавляются; фасады не экспортируют ORM.

Решение, исполнитель/основание и скрытие фиксируются одной транзакцией.
Сбой записи, скрытия или журнала служебного чтения откатывает всю операцию;
служебный материал не возвращается при неуспешной фиксации доступа.
Скрытие не меняет владельческий `updated_at`, не удаляет медиа и не снимается
правкой метаданных, публикацией или обработкой. Потеря Valkey не теряет
жалобы/решения/скрытие; утрата сессии требует нового входа.

Код: `backend/src/moderation/{domain,application,infrastructure,public}`,
HTTP — `app/http/moderation.py`. Video.public.moderation.ReportVideoAccess — внутренние
команды для оркестратора Moderation: повторно проверяют staff-идентичность,
работают в общей транзакции; основание жалобы проверяет и журналирует Moderation.
Tach разрешает импорт этого узкого фасада только инфраструктуре Moderation
и собственным тестам Video; контроллеры, другие модули и общий Video.public
не могут обойти оркестратор жалобы. Разбор медиа и whitelist
файлов у обычной и служебной раздачи общий.

Новые библиотеки, настройки ресурсов, токены просмотра, свободный текст и
фильтры не потребовались. Дополнительная схема Video/User не нужна;
состояние скрытия и роли уже существуют.

## Проверки

Первый профильный набор: 122 теста прошли в Docker. Проверены готовые причины,
одна запись/ревизии/история, очередь 20/20/3 при равном времени, перенос
повторного обращения, обычные роли и живая смена полномочий в существующей
сессии, private/hidden, закрытие завершённой жалобы, конкурентные отправки
и решения, откаты всех записей/скрытия и отказ журнала служебного доступа.
Реальные блокировки PostgreSQL подтверждают проверку новой роли и ревизии
после ожидания. Проверен отказ Valkey без потери постоянных данных.

SQL/HTML/пути во вводе причины или курсоре отклоняются как неверные значения;
отправитель и внутренние ссылки отсутствуют в обычных ответах, служебные
данные не отражаются в ошибках. Свободный текст, shell/XML/сетевые обработчики
не добавляются; произвольный путь не становится ключом RustFS.
DOM/экран модерации остаются до фронтенда.

Ruff/Formatter, Basedpyright, Tach/Tach external, Alembic check и uv audit
прошли. Nginx prod прошёл: реальные сессии, private/hidden, вложенные
AV1/AAC/WebVTT/WebP и декодирование полученного master, GET/HEAD/Range,
решения/повторы/новая ревизия и живая смена moderator → user → admin.
Все запросы фиксируют исполнителя/основание; Python не читает медиабайты.
Расширенная регрессия в Docker прошла: **794 passed** — новые сценарии,
ограничения PostgreSQL, аккаунты/CLI/сессии/DI, архитектура, обычный доступ,
комментарии/лайки, лента/поиск/канал/плейлисты, подготовленная раздача и
готовность при частичном отказе с сохранением hidden. После ограничения
подфасада отдельно прошли **5 архитектурных проверок**: допустим только адаптер
Moderation, контроллер/другие модули/обратный реэкспорт отклоняются.
Это выбранный регрессионный набор, не новый полный прогон всего pytest.

Проверены ограничения причин/ревизий/FK/уникальностей в реальной БД,
сохранение владельческого updated_at при скрытии, типы/CSRF/OpenAPI с
дискриминатором решения, безопасные ошибки и отсутствие неразрешённых
записей после отказов. Локальные ссылки документации и `git diff --check`
проверены; якоря отдельно не проверялись. Аудит секретов dev не повторялся.
