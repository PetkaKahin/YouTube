# Q25: сравнение механизмов серверных сессий

Статус на 2026-11-13: исследование выполнено; пользователь выбрал расширение
starsessions вне пакета. Реализация и её приёмка —
[ADR-0028](../decisions/0028-session-concurrency.md). Ниже сохранены результаты
сравнения до реализации; они не подменяют регрессионные тесты исправления.

## Критерии нашего проекта

- Серверные сессии в Valkey, в cookie только непрозрачный идентификатор.
- Ровно 30 дней без активности, без дополнительного абсолютного ограничения
  для постоянно активного пользователя. Cookie и серверный срок согласованы.
- Поздний запрос не восстанавливает удалённую, истёкшую или потерянную сессию.
- Поздний ответ не возвращает старую cookie после выхода или смены ID.
- Ротация не сохраняет доступ по старому ID; отказ хранилища не открывает доступ.
- Python 3.14.10, FastAPI 0.162.5, Starlette 1.10.0, redis-py 8.1.0,
  pwdlib 0.3.1 и Valkey 9.1.3; бизнес-слои остаются независимыми от HTTP.
- Готовая библиотека управляет идентификаторами и cookie; собственная
  криптография и самостоятельная замена всей системы сессий не вводятся.

## Что фактически проверено

Скачаны wheel опубликованных версий с PyPI, SHA256 сверены с метаданными PyPI.
Эксперименты выполнены в одноразовом dev-контейнере с текущими зависимостями
и настоящим Valkey 9.1.3. Redis SDK загружался из отдельного временного каталога;
pyproject/uv.lock и рабочая интеграция приложения не менялись. Использовались
синтетические сессии в уникальном префиксе; записи удалены после проверки.

| Проверка | Наблюдение |
| --- | --- |
| starsessions: прочитать → удалить → записать старый снимок → прочитать | Сессия восстановлена |
| Примитив SET XX после удаления | Запись отклонена, ключ не создан; это проверка примитива, не готового адаптера |
| Redis SDK: прочитать → удалить → сохранить старый снимок → загрузить | Старую сессию загрузить нельзя |
| Redis SDK: истечение idle TTL → сохранить старый снимок → загрузить | Старую сессию загрузить нельзя |
| Redis SDK: удержать запрос с изменённым снимком → выйти параллельным запросом → завершить удержанный | Удержанный ответ выдаёт старую cookie; старая сессия при этом недействительна |
| Redis SDK: удержать запрос → сменить идентичность и ID параллельным запросом → завершить удержанный | Удержанный ответ выдаёт старую cookie, которая может перезаписать новую в браузере |
| Redis SDK: idle_ttl=10, absolute_ttl=0, gc_ttl=2; чтение каждые 0,5 секунды | Результаты: жива, жива, отсутствует, отсутствует, отсутствует. Эффективный абсолютный срок равен 2 секундам |

В последних двух конкурентных пробах порядок обеспечивался событиями:
удержанный запрос уже загрузил снимок, второй запрос завершился, после этого
первому разрешалось отправить ответ. Это воспроизведение определённого порядка,
а не нагрузочный тест всех возможных чередований. Возврат старой cookie в SDK
не означает восстановление авторизации: сервер её отвергает, но пользователь
может потерять только что обновлённую сессию.

Уменьшенные сроки в пробе проверяют механизм; ожидание 30 дней не проводилось.
У SDK absolute_ttl=0 подставляет gc_ttl в неизменяемый срок ключа. Увеличение
этого значения только отодвигает предел, не превращает его в rolling-срок.

SHA256 исследованного Redis SDK wheel 0.9.1:
`e4d1162b8187b0d3dadcaec5e239c95df3f12b2ba109b15661e96e138ffae2bf`.
Код основной ветки уже объявляет 0.10.0; выводы runtime относятся к wheel 0.9.1.

## Рекомендация и границы её достоверности

Из рассмотренных вариантов рекомендуется сохранить starsessions и добавить
ограниченное расширение: атомарное сохранение/отзыв через штатный SessionStore
и контроль выдачи сессионной cookie. Один только новый RedisStore недостаточен:
starsessions после write самостоятельно выставляет Set-Cookie.

Это наименьшая совокупная область изменений для текущего стека, а не утверждение,
что ещё не написанный адаптер уже надёжен. Для принятия исправления обязательны
проверки позднего сохранения после выхода/ротации/истечения/удаления из Valkey,
порядка cookie при параллельных ответах, rolling TTL, нескольких экземпляров
приложения, ошибок хранилища, отмены запроса и стриминга. При ротации нужно
проверять и запрет переноса отозванного снимка под новый ID без новой аутентификации.

Ротацией ID, сериализацией и формированием cookie продолжает управлять библиотека.
Генератор идентификаторов и новый механизм входа этой доработкой не создаются.
Пользователь принял рекомендацию; реализация выполняется по ADR-0028.
Альтернативные библиотеки в проект не установлены. Подготовка коммита в master
включает отдельную приёмку реализованного расширения.
