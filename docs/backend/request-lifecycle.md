# Жизненный цикл приложения и HTTP-запроса

Статус: техническая основа реализована в рамках [T02](../tasks/T02-backend-foundation.md).
Реализованы аккаунты, регистрация и HTTP login/me/logout; ресурсные политики пока не реализованы.
Согласованные HTTP-правила — [ADR-0022](../decisions/0022-http-foundation.md).

## Сборка и ресурсы

`app/main.py:create_app` собирает приложение. `app/settings.py` использует
pydantic-settings для несекретных значений environment; `.env` внутри Python
не читается. Пароли и CSRF-ключ читает `app/secrets.py` только из файлов
Compose Secrets. Клиент Valkey и CSRF-ключ подготавливаются фабрикой; соединения
открываются при работе lifespan. Отсутствие ключа не позволяет запустить API.

Lifespan получает из APP-провайдера Dishka AsyncEngine SQLAlchemy/Psycopg,
фабрику AsyncSession и S3-клиент boto3. Один redis-py клиент используется кэшем и RedisStore starsessions.
Старт проверяет PostgreSQL (`SELECT 1`), Valkey (`PING`) и RustFS (`HEAD bucket`).
При недоступности зависимости старт завершается с безопасной диагностикой.
Контейнер закрывает провайдеры при остановке и частичном сбое запуска;
внутренний AsyncExitStack освобождает созданные ресурсы;
`app.state.resources` очищается. Синхронный S3-вызов выполняется в потоке,
долгие видеооперации остаются будущими фоновыми сценариями.

`app.state.password_hash` содержит pwdlib с Argon2id, `app.state.authorization` —
адаптер Casbin через независимый `common.contracts.authorization.Authorization`. Начальный
набор разрешений пуст: любой вызов политики запрещает доступ. Это точка сборки
будущих зависимостей, а не реализация входа или проверка доступа к видео.

## DI и время жизни

`app/di.py` содержит `ApplicationProvider` и фабрику async-контейнера Dishka.
`APP`: настройки, Redis, ресурсы, engine, S3, авторизация и хеширование.
`REQUEST`: отдельная `AsyncSession`, закрываемая после ответа, включая стриминг
и ошибки. Повторное получение в одной области возвращает тот же объект.
Commit не выполняется автоматически; незавершённая транзакция откатывается
при закрытии сессии. Контейнер проверяет граф при сборке.

`app/main.py` подключает `FastapiProvider` и `setup_dishka`; роутер использует
`DishkaRoute`, а контроллеры — `FromDishka[Тип]`. Служебная readiness получает
ресурсы именно так. Вне HTTP фабрика `create_container(settings, cache)`
даёт тот же набор зависимостей: `async with container() as operation`, затем
`await operation.get(AsyncSession)`. Владелец контейнера обязательно вызывает
`await container.close()` в `finally`.

`app/module_providers.py` явно импортирует провайдеры из `infrastructure/di.py`
пяти модулей. Фабрика контейнера добавляет их после `ApplicationProvider`,
затем дополнительные провайдеры вызывающей стороны (например, FastAPI).
UserProvider и ChannelProvider регистрируют сценарии аккаунтов/регистрации
и реализации их портов. SqlTransactions использует ту же REQUEST-сессию БД.

Бизнес-код сохраняет обычные конструкторы и не импортирует Dishka. Контроллеры
получают сценарии через публичные контракты. Доступ к провайдеру разрешён только
техническому реестру и собственным тестам модуля, остальные внутренности закрыты.
[ADR-0025](../decisions/0025-dishka.md),
[ADR-0027](../decisions/0027-explicit-module-providers.md).

## Запрос и ответ

Порядок входа: ASGI middleware жизненного цикла → CSRF → сессия → автозагрузка
сессии → область REQUEST Dishka → роутинг/валидация FastAPI → сценарий. Ответ проходит цепочку
в обратном направлении. Неизвестные HTTP-маршруты обрабатываются теми же
обработчиками ошибок. Служебный `GET /api/v1/health/ready` публичный и возвращает
`200 {"status":"ready"}` либо `503` в общем формате ошибок. Docker healthcheck
Python проверяет именно этот маршрут.

`RequestLifecycleMiddleware` создаёт серверный UUID `request_id`, кладёт его
в `request.state` и `X-Request-ID`; клиентское значение не принимается как доверенное.
Один журнал завершения содержит метод, шаблон маршрута, статус и полную длительность.
Для неизвестного маршрута пишется `<unmatched>`, без сырого пользовательского пути.
Тела, query, cookie, токены и тексты исключений в журнал не включаются.
Стандартный access log Uvicorn отключён; access log Nginx также исключает URL/query.
Непредвиденная ошибка до начала ответа превращается в безопасный `500`.
После начала потока ответ уже нельзя заменить JSON: поток прерывается,
фиксируется ошибка, наружу пробрасывается исключение без исходных деталей.
Middleware не буферизует поток и не делает commit транзакции.

## JSON и ошибки

Входные JSON-схемы наследуют `common.http.schemas.JSONModel`:
`strict=True`, `extra="ignore"`. Например, `"2"`, `2.0` и `true` не подходят
для целочисленного поля; неизвестные поля удаляются, в том числе во вложенных
схемах, наследующих ту же основу. Path/query, multipart и доменные значения
потребуют собственных контрактов при реализации сценариев.

Ошибки используют `application/problem+json`: `type`, `title`, `status`,
`detail`, `code`, `request_id`, `errors`. Для стандартных ошибок `type=about:blank`.
Ошибка поля содержит только `location` и машинный `code`; входное значение,
Pydantic context и внутренние сообщения исключений не возвращаются.
Общий обработчик сохраняет служебные HTTP-заголовки, например `Allow`.

`app/http/routing.py` собирает `/v1` и общие описания ошибок контроллеров.
`app/http/accounts.py` предоставляет POST `/auth/register` (201), POST `/auth/login`
(200), GET `/auth/me` (200/401), POST `/auth/logout` (204).
Регистрация не выполняет вход автоматически. Конфликты email/тега — 409 с ошибкой
поля, остальные ошибки регистрации — 422; неизвестный email и неверный пароль
при входе дают одинаковый 401 invalid_credentials.
`app/http/videos.py` предоставляет POST `/videos` (201), GET/PUT
`/videos/{id}/settings` (200). Владелец определяется сессией; чужой и отсутствующий
ID дают одинаковый 404, отсутствующий аккаунт/сессия — 401. Подмена owner_id
и служебных состояний в body не меняет серверные данные. Невалидные метаданные — 422.
Нормализация и ограничения — [Video](modules/video.md). Ответы настроек имеют
Cache-Control: no-store и Vary: Cookie. Создание/изменение требует CSRF.
OpenAPI регистрирует общие схемы
с корректными ссылками `#/components/schemas/...`.

## Swagger UI и префиксы

Внешние адреса: `/docs` перенаправляет на `/api/docs`; схема —
`/api/openapi.json`, прикладные маршруты — `/api/v1/...`.
Nginx снимает `/api`, Uvicorn получает `UVICORN_ROOT_PATH=/api` и формирует
ASGI root_path. Устаревший аргумент FastAPI `root_path` не используется.
Изнутри Docker доступны `http://python:8000/docs`, `/openapi.json`, `/v1/...`.

Swagger UI показывает операции и позволяет выполнять запросы. Для небезопасных
методов OpenAPI объявляет `X-CSRFToken` как API key header: в Authorize нужно
вставить значение cookie `csrftoken`, полученной при открытии документации.
Браузер отправляет сессионную cookie сам; JWT/Bearer не вводятся.
У защищённых изменяющих операций SessionCookie и CSRFToken входят в одно
требование OpenAPI (оба обязательны); это соответствует реальным middleware.

## Сессии и границы текущей готовности

starsessions настроен на rolling 30 дней, наш GuardedRedisStore использует префикс
`sessions.`. Cookie `session`: Path=/, HttpOnly, SameSite=Lax;
`csrftoken`: Path=/, SameSite=Lax, доступна JavaScript. В prod обе Secure,
в локальном dev по HTTP — без Secure. Все небезопасные запросы требуют
подписанную CSRF-cookie и совпадающий заголовок X-CSRFToken, в том числе до входа.
CSRF-отказ возвращает `403` Problem Details.

Расширение Q25 находится вне пакета: `common/infrastructure/session_store.py`
реализует штатный SessionStore; `common/http/sessions.py` оборачивает библиотечный
SessionMiddleware. Адаптер создаётся отдельно на каждый запрос, соединение Valkey
общее. Новая запись использует NX, действующая — XX. Если запись исчезла после
загрузки, ответ не восстанавливает её и не выставляет сессионную cookie.

Для входа и смены привилегий использовать `rotate_session`: ID генерирует
starsessions, Valkey атомарно переносит ещё живой старый ключ на свободный новый.
Если старый ключ уже отозван/истёк, ротация возвращает 409 без cookie. Для гостя
сначала резервируется новый ID пустой записью с TTL; затем данные сохраняются с XX.
Потеря этой записи до ответа не создаёт авторизованную сессию заново.
`end_session` удаляет запись и очищает данные; повторное удаление в запросе
идемпотентно. Поздний выход по уже перенесённому ID не удаляет новую cookie.
Прямой вызов regenerate_session_id в обход нашего helper не поддерживается.

Обёртка подавляет только сессионный Set-Cookie отклонённой записи, сохраняя другие
cookie. Ответы с кодом >=400 не сохраняют новые данные сессии и не продлевают её.
Потоки не буферизуются; тело после отправки заголовков повторно сессию не сохраняет.
Нет блокировки вокруг всего запроса. Уже начатые сценарии и отправленные ответы
отзыв сессии не откатывает. Порядок доставки уже отправленных cookie по разным
соединениям сервер не контролирует; отозванный ID остаётся недействительным.

Проверены управляемые гонки выхода/ротации, две ротации, поздний выход, истечение
и удаление записи до сохранения, резервирование нового ID, ошибки Valkey, отмена
и стриминг, в том числе два независимых экземпляра middleware. Описание —
[ADR-0028](../decisions/0028-session-concurrency.md),
[сравнение альтернатив](session-options.md). Стабильный релиз starsessions остаётся
2.2.1; в предварительном 2.3.0a1 и основной ветке гонка RedisStore ещё присутствует.

При login сессия ротируется и получает только user_id; GET me проверяет этот
серверный идентификатор и читает аккаунт/роль из PostgreSQL без кэша роли.
Logout вызывает end_session, удаляет запись Valkey и cookie; повтор безопасен.
Casbin пока содержит техническую модель RBAC без разрешающих правил.
Ресурсные ABAC-проверки, приватность и служебный просмотр добавляются в B-задачах.

## БД и миграции

Общая ORM metadata с соглашениями имён — `common/infrastructure/database.py`.
Конкретные таблицы принадлежат infrastructure своего бизнес-модуля.
`backend/alembic.ini` и `migrations/` подготавливают Alembic; пароль берётся
из secret-файла, URL не записывается в конфиг и не выводится в журнал.
DDL при старте приложения не выполняется. Миграция 0001 создаёт user_accounts
и channel_profiles с bigint identity, уникальностями и ограничениями.
Alembic получает metadata через `app/orm.py`: штатный реестр провайдеров загружает
собственные адаптеры и ORM-модели модулей. `public` не регистрирует модели,
скрипт миграций не импортирует внутренние пакеты бизнес-модулей.

Команды после запуска dev:

```bash
./docker/run dev exec python alembic check
./docker/run dev exec python alembic revision --autogenerate -m 'описание изменения'
./docker/run dev exec python alembic upgrade head
```

Сначала проверить сгенерированную миграцию; её создание требуется только при
реальном изменении схемы. Фабрика AsyncSession не задаёт автоматический commit
на HTTP-ответе: границей транзакции управляет сценарий.
