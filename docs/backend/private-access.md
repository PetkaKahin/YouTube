# Приватный доступ по email и просмотр метаданных

Реализованы разрешения и просмотр метаданных B20/B21 по [ADR-0009](../decisions/0009-private-access-by-email.md)
и [правилам Video](modules/video.md#применение-доступа).

Разрешения хранят нормализованный email без FK на аккаунт: список не раскрывает
существование получателя. Формат/нормализация используются из User.public,
без DNS и поиска аккаунта по адресу. Получатель входит с этим email;
подтверждения почты нет по согласованному упрощению.

GET `/api/v1/videos/{id}/permissions?cursor=...` возвращает владельцу
emails (до 20) и next_cursor по ADR-0059/0060.
PUT того же пути принимает email и целевое allowed (true/false). Повтор
идемпотентен; адрес в URL не передаётся. Список можно менять в черновике,
при public и private; переключение видимости его не стирает. Разрешения
используются при private. Изменение списка — правка владельца: updated_at
меняется только при реальном изменении, added_at сохраняется. Строка публикации
сериализует настройки и разрешения. Новых количественных лимитов не вводится.

## Пагинация разрешений

GET permissions принимает необязательный cursor и возвращает emails (до 20)
и next_cursor (null в конце). PUT сохраняет тот же вход и возвращает первую
страницу этого же формата после изменения внутри общей транзакции.
Новые выдачи выше прежних; нормализованный повтор не меняет место/updated_at,
отзыв и новая выдача создают новую позицию. Список не фиксирует снимок:
новые выдачи выше cursor появляются после обновления первой страницы,
удаление границы не мешает продолжению. Количество разрешений не ограничивается.

Миграция 0019 добавляет числовой identity ключ записи, уникальность ключа
и индекс (video_id, id DESC), сохраняя PK(video_id,email) и сами разрешения.
Исторические даты выдачи неизвестны: старый набор сохраняет алфавитный порядок,
новые записи получают ключи выше существующих. Новых таблиц/библиотек/секретов нет.
Сценарий читает максимум 21 строку до формирования страницы, без OFFSET.

Курсор — версия/вид списка/ID видео/ID владельца/граница ID; адресов и других
персональных данных в нём нет. Он не даёт прав, не подписывается и не содержит
состояния сессии. Проверка владельца предшествует декодированию. Чужой контекст,
неверная версия/граница/кодирование и повтор cursor-параметра дают общий 422
без отражения ввода. Гость/посторонний/сотрудник не читают чужие разрешения.
Ответы no-store/Vary Cookie; сбой чтения после изменения откатывает транзакцию
и не выдаёт частичный список. Отзыв просмотра не зависит от страницы, на которой
находился адрес.

## Обычный просмотр

GET `/api/v1/videos/{id}` отдаёт только доступные зрителю метаданные и готовые
качества. Для каждого запроса нужны published, visible, хотя бы один полностью
готовый AV1/AAC и право: public доступно гостю; private — вошедшему владельцу
или разрешённому email. Роль сотрудника прав просмотра не даёт. Скрытое видео
недоступно обычным сценарием даже владельцу; настройки владельца независимы.

Casbin исполняет статическую ABAC-политику по серверным атрибутам. Метаданные,
состояния медиа и актуальное разрешение читаются одним SQL-снимком. Проверка
не использует потеряемый кэш: отзыв применяется к последующим запросам после
commit. Недоступное и отсутствующее видео имеют одинаковый 404 без частичных
данных. Успешные ответы и ожидаемые отказы — no-store/Vary: Cookie.
Неожиданный отказ БД даёт общее сообщение без бизнес-данных.
Разрешённый зритель не получает
служебных статусов/ошибок, общих media ID, ключей RustFS или списка email.

Новая таблица video_private_grants (миграция 0015). Домен и сценарии не зависят
от HTTP/SQLAlchemy/Casbin; адаптеры читают чужой модуль только через User.public.
Общий порт Authorization допускает доверенные объекты ABAC наряду с прежними
строками RBAC; Video имеет собственную статическую модель без изменяемых
персональных политик в singleton-enforcer.

Подтверждение публикации и защищённая доставка добавлены последующим этапом
[B11/B22](media-delivery.md); RustFS остаётся закрытым.
[Главная](feed.md) и [поиск](search.md) исключают private независимо от
персонального разрешения; публичные списки каналов проверены в B06.
Интерфейс списка адресов остаётся до фронтенда.

Все медиамаршруты используют те же свежие проверки доступа; HTTP-метаданные
содержат ссылки hls_url/preview_url конкретной публикации. B20 закрыт
после проверки главной, поиска, плейлистов и канала в B06.

Приёмка: одинаковые ответы до/после регистрации адресата; нормализация, повторы,
валидация, CSRF, роли/владение, конкурентные изменения и rollback, матрица
просмотра, раннее низкое качество, отзыв/смена видимости/скрытие, потеря сессии,
отказ БД, инъекции и отсутствие лишних данных/медиа в ответах.
