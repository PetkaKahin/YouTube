# Превью видео

Бэкенд B16 реализован по [ADR-0054](../decisions/0054-thumbnail-selection.md):
постоянные задания, общие кадры/WebP, собственные изображения и API владельца.
Зрительская и owner-выдача байтов подключены через Nginx в
[B22](media-delivery.md). Интерфейс выбора ещё не реализован.

Основная видеодорожка даёт одну общую работу на тройку кадров. Позиции случайны
и воспроизводимы по слепку/версии профиля, распределены по трём частям ролика.
Проба чёрного кадра заменяется кадром из середины той же трети; у целиком
чёрного ролика сохраняется доступный кадр. Короткий или статичный ролик может
дать совпадающие варианты: одинаковые пиксели внутри пакета кодируются/хранятся
один раз. Первый вариант используется до ручного выбора. У каждой публикации собственный
выбор, общий пакет не содержит метаданных и прав владельца.

Своё изображение передаётся напрямую в RustFS по одночастному multipart-плану,
как исходник, но с лимитом 10 МиБ. Проверка содержимого выполняется в фоне:
до 40 мегапикселей, без доверия имени/MIME. У многокартинного контейнера
выбирается основное изображение (default, иначе первое, обычное предпочтительнее
attached picture); второй кадр выбранной дорожки отклоняет анимацию.
Декодер читает только открытый FD, без вложенных сетевых/локальных URL.
FFmpeg получает `max_pixels=40000000` ещё до открытия своего изображения;
геометрия дополнительно проверяется по отчёту. Нормализованные RGBA-пиксели
с учётом геометрии и версии профиля хешируются до WebP; общие результаты кодируются
отдельным идемпотентным заданием. Промежуточные данные остаются до готовности.

Тяжёлая работа вне HTTP и транзакций. Данные намерения, очередь и ссылки
фиксируются транзакционно. Поколение/токен, журнал и очистка используют существующие
правила кодирования; старый worker не заменяет новый выбор. Ошибка своего файла
не стирает прежнее превью и не переводит успешно кодируемое видео в failed.
Дата изменения меняется при ручном выборе/подтверждении своего изображения,
а не при фоновом завершении. Готовность и просмотр подключены в
[B18](readiness.md)/[B22](media-delivery.md).

## Данные, очередь и очистка

Начальная [схема БД](database-schema.md) содержит
`video_thumbnail_uploads`, `video_thumbnail_choices`, `video_thumbnail_preparations`.
Эти таблицы сохраняют
поколение намерения и подтверждение выбора, разрешая отдельные параллельные
передачи своих изображений без общего перезаписываемого входного ключа.
У общего `video_encoded_tracks` ровно один источник: видео или подготовленное
изображение. Генерация тройки записана в постоянном плане; старые планы
дополняются обслуживанием, без повторного кодирования готового AV1/AAC.
В общей очереди только числовые ID. Минимальные аудио/видео сохраняют приоритет
перед тройкой кадров, затем продолжаются старшие качества. Отдельная подготовка
своего изображения приоритетна и не пересоздаёт общую тройку или AV1/AAC.

Задание `video.prepare_thumbnail` проверяет и нормализует свой файл в RGBA.
Далее общий `video.encode_track` получает kind=thumbnail_image/thumbnail_set
и тот же механизм токена/поколения, приватного префикса попытки и фиксации ready,
что AV1/AAC. Проверяются декодируемость, число кадров и фактические размеры
каждого WebP; имена только серверные, описательные теги не переносятся.
Скрипты SVG не выдаются клиенту.

Незавершённые префиксы подготовки имеют собственный срок попытки +60 с.
Обслуживание удаляет просроченный префикс под блокировкой, если он не активен
и не является сохранённым источником общего результата. После готовности WebP
обслуживание удаляет вход своего изображения и промежуточные пиксели;
запись подтверждённой передачи остаётся для идемпотентного complete.
При ошибке источники сохраняются для повторов. Старый выбор не стирается при
ошибке нового файла; новое ручное решение определяется сохранённым requested ID,
а не порядком окончания worker.
Каждый POST старта своего файла создаёт отдельную передачу и новое поколение
выбора; refresh продолжает конкретную передачу. Ручной выбор кадра также меняет
поколение. Подтверждение старой передачи завершает её обработку, но не применяет
старый выбор. Автоматическое восстановление ставит работу в очередь; выбор
и дату изменения подтверждает только запрос владельца.

TIFF с поддержанными метаданными не отклоняется только из-за режима
`err_detect=explode`: для изображений используются `-xerror` и отказ при error-stderr,
а также проверка полного кадра. Строгий режим проверки видео не ослаблен.

## API владельца

Все пути ниже с префиксом `/api/v1/videos/{video_id}/thumbnail`:

| Метод и окончание пути | Результат |
| --- | --- |
| GET пустой путь | status, selected, slot, готовые candidates, current_url, custom_status/error_code |
| PUT пустой путь, `{slot: 0..2}` | Выбор готового предложенного кадра, отмена ожидающего своего превью |
| GET `/image` | Текущий готовый image/webp |
| GET `/generated/{slot}` | Один из готовых предложенных кадров |
| POST `/upload`, `{size}` | Одночастный план прямой передачи, не более 10 МиБ |
| POST `/upload/{upload_id}/refresh` | Обновление URL по существующей политике 15 минут/24 часа |
| POST `/upload/{upload_id}/complete` | Серверное подтверждение и атомарная постановка подготовки |

Ответы no-store/Vary Cookie, изменения требуют сессию/CSRF. Ключи RustFS и
внутренние общие идентификаторы не выдаются. Публичной раздачи этот этап не добавляет.
Чужой и отсутствующий ID дают один 404; гость — 401. Готовность/ошибка своего
изображения не меняет дату добавления, публикацию, видимость и processing видео.

Код: [правила](../../backend/src/video/domain/thumbnails.py),
[сценарии](../../backend/src/video/application/thumbnails.py),
[SQL](../../backend/src/video/infrastructure/thumbnail_jobs.py),
[FFmpeg/RustFS](../../backend/src/video/infrastructure/thumbnail_media.py),
[HTTP](../../backend/src/app/http/thumbnails.py).

## Проверки

Реальные PostgreSQL/RustFS/FFmpeg/Procrastinate, ограниченный dev-контейнер:
[сценарии](../../backend/src/video/tests/test_thumbnails.py),
[лимиты](../../backend/src/video/tests/test_thumbnail_limits.py),
[сбои/поколения/очистка](../../backend/src/video/tests/test_thumbnail_recovery.py),
[порядок выбора/подтверждений](../../backend/src/video/tests/test_thumbnail_intents.py),
[HTTP/CSRF/сессии и подписанный PUT](../../backend/tests/test_thumbnails_http.py).
Проверены PNG/JPEG/WebP/BMP/TIFF/AVIF/ICO, растеризация SVG, повреждённый ввод,
анимация, RGBA-дедупликация, предыдущий/новый выбор и неизменность дат при работе фона.
HDR→SDR проверяется в [медиа-тестах](../../backend/src/video/tests/test_encoding_media.py).

Для SVG проверены отсутствие обращений к HTTP-ловушке и совпадение пикселей
с вариантом без внешнего файла. FFmpeg использует librsvg `new_from_data`
без base URI; внешние file/http-ссылки не разрешены. Первичные источники,
проверены 2026-11-14:
[FFmpeg 7.1.5](https://raw.githubusercontent.com/FFmpeg/FFmpeg/n7.1.5/libavcodec/librsvgdec.c),
[правила librsvg](https://gnome.pages.gitlab.gnome.org/librsvg/Rsvg-2.0/class.Handle.html#security-and-locations-of-referenced-files).

Prod-проверка без pytest и Valkey воспроизводится отдельной БД и тестовыми
объектами; скрипт удаляет их и при ошибке:

```bash
./docker/run prod run --rm -T --no-deps media-worker python - < docker/python/check_thumbnails.py
```

Скрипт проверяет общую тройку двух аккаунтов, независимый выбор, одинаковые
пиксели PNG/BMP до WebP, SHA-256/декодирование изображений, анонимный HTTP 403
RustFS и очистку временных изображений. Полная приёмка плеера/каталога и
визуальное соответствие YouTube остаются до задач UI; каталог B23 подключён,
сквозная раздача проверена в [B22](media-delivery.md).
Следующий этап расширил этот же скрипт встроенным mov_text и общим WebVTT;
результаты обработки субтитров описаны [отдельно](subtitles.md).

Результаты этапа:

  миграцией 0012: **26 профильных тестов прошли**, включая четыре новых случая
  позднего complete, двух одновременных передач и сбоя между приёмом файла
  и подтверждением выбора. После уточнения обновления ORM-состояния отдельно
  прошли **20 тестов** выбора/HTTP/форматов; полный набор после 0012 не повторялся.

  Проверены 115 Markdown-файлов и 1040 локальных ссылок; `git diff --check` чистый.

Поддержка всех профилей произвольного формата этим не обещается: требуется
корректный разбор установленным FFmpeg. С 2026-11-16 произвольные повороты
используют [общую геометрию и полный холст](encoding.md#границы-этапа):
SAR, направление и все углы кадра сохраняются, HDR преобразуется в SDR.
Одинаковое преобразование применяется к трём кадрам видео и собственному
изображению владельца. Вырожденные/перспективные матрицы и текст вместо
числовых коэффициентов отклоняются до запуска фильтра.
