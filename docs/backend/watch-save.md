# Сохранение доступного видео в свои плейлисты R20

Статус: `done`, серверная часть. [Согласованные правила и HTTP-контракт](../frontend/watch-save-backend-request.md).
Отдельные сценарии просмотра позволяют включать доступное видео любого автора
в собственные public/unlisted/private-плейлисты. Studio сохраняет owner-only API.

Схема БД и медиапакеты не меняются: существующая уникальная пара playlist/video
уже поддерживает включение видео разных авторов. Новых миграций и библиотек нет.

Channel вызывает Video.public.RequirePlaylistVideo для обычной проверки просмотра
под разделяемой блокировкой публикации, затем блокирует канал текущего аккаунта.
Этот порядок совместим с Studio: видео, затем канал. Смена доступа/отзыв/скрытие
сериализуются с сохранением. Изменения одной пары сериализованы с полным набором
Studio, без удаления чужих включений. Метаданные видео не меняются от закладки.
Даты плейлиста и порядок меняются только при реальном включении/исключении.

GET saved-playlists использует отдельное назначение cursor, аккаунт и video_id;
saved вычисляется по всему собственному набору. Создание с video_id проверяет
просмотр и создаёт плейлист/пару в общей транзакции; при отказе всё откатывается.
Чтение состава остаётся пакетным и проверяет каждый ролик независимо от автора.

Проверки охватывают только новые сценарии, совместимость Studio и затронутые
пути чтения плейлистов/канала; общий прогон и медиаконвейер не требуются.

## Код и проверка

Channel.public экспортирует GetSavedPlaylists, SetSavedPlaylist и DTO
SavedPlaylistList/SavedPlaylistSelection:
[сценарии](../../backend/src/channel/application/watch_save.py),
[создание с включением](../../backend/src/channel/application/playlists.py),
[адаптеры и пары](../../backend/src/channel/infrastructure/playlists.py),
[HTTP](../../backend/src/app/http/playlists.py).
[Video.public.RequirePlaylistVideo](../../backend/src/video/application/playlist_cards.py)
участвует в транзакции Channel и использует собственный порт блокировки Video.
Owner-only сценарий PlaylistVideoOwnership не меняет своих правил.

В Docker прошли **20 профильных HTTP/БД-проверок**:
[тесты R20](../../backend/tests/test_watch_save_http.py). Использованы готовые
медиапакеты без повторного кодирования. Проверены:

- Гость/CSRF/поля и точные int64, OpenAPI, пустой список, три режима плейлистов,
  обычное создание и атомарное создание с чужим видео.
- Пагинация 20/21 при равных датах, отдельный cursor по аккаунту/видео/назначению,
  saved=true для включения за первой страницей и одно чтение членства без N+1.
- Повторы true/false без изменения дат и порядка, снятие одной пары при сохранении
  остальных, удаление/новое включение в конец, параллельные разные пары без потерь.
- Разрешённое private, отзыв и восстановление доступа без удаления сохранений,
  admin без обхода прав, hidden/draft/неготовое/отсутствующее видео и чужой плейлист.
- Studio не меняет чужое видео и не удаляет сохранения других пользователей;
  состав возвращает настоящих авторов разных видео, public/unlisted/private
  и публичный список плейлистов канала сохраняют прежние права.
- 43 недоступных включения перед 23 доступными не сокращают страницы состава
  20/3; cursor и порядок сохранены. Чтения не создают прогресс или лайки.
- Сбой вставки/обновления откатывает создание вместе с парой; сбой после удаления
  пары откатывает удаление/дату без потери остальных сохранений. Отказ зависимости
  не возвращает частичный список. Выигравшее блокировку изменение приватности
  отклоняет ожидающие PUT пары и создание с видео.

Ruff, форматирование и Basedpyright затронутых файлов прошли. В работающем dev
через Nginx подтверждены методы/DTO/CSRF в OpenAPI, 401 гостя и 200 GET с сессией.
Общие проверки приложения и тесты фронтенда не запускались.
