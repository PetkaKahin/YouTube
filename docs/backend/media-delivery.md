# Публикация и защищённая доставка медиа

Реализованы B11/B22 по [ADR-0055](../decisions/0055-nginx-media-delivery.md).
Схема БД не менялась; использованы постоянные состояния и дескрипторы конвейера.

POST `/api/v1/videos/{id}/publish`: сессия/CSRF и владение, завершённая передача
исходника обязательна. Готовность первого качества не требуется. Публикация —
явная правка владельца: только переход draft → published меняет updated_at;
повтор не меняет даты. added_at, private, hidden, обработка и разрешения
сохраняются. После очистки оригинала подтверждение работает по постоянному
факту принятой загрузки, без HEAD удалённого файла.

GET/HEAD `/api/v1/videos/{id}/hls/master.m3u8` и
`/api/v1/videos/{id}/hls/tracks/{track}/{file}` проверяют те же условия, что
метаданные: published + visible + готовый вариант + public/owner/email.
В master только полные AV1/AAC и совместимые WebVTT. Внешние track — логические
ссылки публикации (v1/a1/s1-2), физические ID/ключи/подписи не выдаются.
Каждый запрос файла проверяет принадлежность актуальному готовому master;
знание чужого track, прежней ссылки или имени файла не открывает объект.

GET/HEAD `/api/v1/videos/{id}/preview.webp` возвращает текущее выбранное превью
с той же проверкой доступа. Пока новая собственная картинка не готова,
сохраняется предыдущее готовое превью. Owner API выбора остаётся отдельным.
Байты трёх кандидатов и текущего изображения в owner API также передаются
через Nginx; проверка владения разрешает их в черновике и при скрытии, как прежде.
HTTP GET/HEAD не скачивают изображения в Python.

FastAPI генерирует небольшие master/media playlists по проверенным дескрипторам,
а для прочих файлов отдаёт X-Accel-Redirect. Nginx использует только фиксированный
RustFS upstream, не передаёт ему cookie/Authorization клиента, не кэширует
разрешения и ответы, не раскрывает подпись через Location/ошибки. Внутренний
маршрут закрыт для внешних запросов; обрабатываются GET/HEAD и byte Range.
Обычный одиночный Range передаётся RustFS. При If-Range Nginx проверяет ETag
полного ответа; несовпадение возвращает 200 целиком. Потоковая выдача может
игнорировать запрос нескольких диапазонов и возвращать 200 целиком.
Новые TTL и квоты не вводятся. Неожиданные ответы RustFS заменяются общими
ошибками, без XML и ключей; 404 и 416 сохраняют безопасную семантику.

Приёмка: полный путь через настоящие Nginx/FastAPI/RustFS в изолированной БД,
публикация до/после готовности и очистки оригинала, готовые низкие качества,
AV1/AAC/WebVTT/WebP, HEAD/Range, гость/владелец/получатель/посторонний,
отзыв/private/hidden на следующем запросе, внутренний путь/прямой RustFS,
подмена track/имени/метода/заголовков, отсутствие утечек в ошибках/логах,
прерванный ответ хранилища и сохранность бизнес-состояний при отказах.

## Реализация и проверка

Код: [сценарии доставки](../../backend/src/video/application/delivery.py),
[адаптер плейлистов и S3-подписи](../../backend/src/video/infrastructure/delivery.py),
[публикация](../../backend/src/video/application/publications.py),
[HTTP](../../backend/src/app/http/media.py),
[Nginx](../../docker/nginx/api.conf).

В Docker прошли 113 профильных проверок сценариев, БД, HTTP/CSRF/сессий,
владения и OpenAPI (группы пересекаются с прежними проверками).
Ранние 360/480 доступны до завершения 720 и после его отказа; запрос 720
в это время закрыт. Проверены публикация до готовности, независимость private/hidden,
отсутствие HEAD исходника, параллельные повторы и rollback после изменения БД.
Полная регрессия: **923 passed за 898,67 с**, 2 CPU/8 ГиБ без дополнительного swap.
Ruff/Formatter (197 файлов), Basedpyright, оба Tach, Alembic check, uv audit
(85 пакетов), Compose dev/prod config, Nginx config и HTTP smoke прошли.
Аудит секретов: 11 контейнеров, 72 поверхности, argv/environment прочитаны
без пропусков, findings=[], status=pass. Dev-окружение восстановлено на прежнем
локальном порту 18080, worker перезапущены.

`./docker/check_delivery dev` и `prod` прошли на соответствующих собранных образах.
Квалификация создаёт отдельную БД и два временных контейнера без внешних портов.
Используются настоящие Nginx/FastAPI/RustFS, конвейер AV1/AAC/WebVTT/WebP и
два владельца с физически общими результатами. Проверяются все вложенные URL,
HEAD с длиной GET, Range/416/If-Range, выбор/три owner-кадра, чужой/отозванный доступ,
смена private/public и hidden, внутренний путь, подмена URL/метода/заголовков,
закрытый RustFS, отсутствие ключей/подписей в плейлистах и HTTP-ответах.
Все варианты скачанного master декодируются FFmpeg, текст/время VTT проверяются.
Весь HTTP-этап проходит с запрещёнными get_object/head_object в клиенте FastAPI:
контроллеры не читают медиабайты, включая изображения владельца.

TCP-посредник только в квалификации пересылает запросы в реальный RustFS и
однократно обрывает ответ после настоящих заголовков и первого байта. Клиент
обнаруживает неполную передачу, следующий запрос успешен; состояния и даты
видео не меняются. Отдельно проверены удалённый объект (общий 404) и неверная
внутренняя подпись (общий 502), без XML/URL/секретов в ответе. Посредник отсутствует
в приложении. HTTP-сессии теста удаляются, собственные объекты и БД убираются.

Prod собран штатным Dockerfile, без pytest. Отдельная квалификация
[check_thumbnails.py](../../docker/python/check_thumbnails.py) прошла с принудительным
отказом Valkey: конвейер, очистка исходников, публикация и права метаданных постоянны.
Фронтенд-плеер/DOM, каталог/поиск и служебный просмотр по жалобе в этап не входят.

Документы: 120 Markdown-файлов, 1180 локальных ссылок ведут на существующие
файлы; якоря отдельно не проверялись. `git diff --check` чистый.
