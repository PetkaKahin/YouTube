# Постоянный приём исходника в обработку

Реализовано 2026-11-14: завершённая передача атомарно связана с заданием
Procrastinate, проверка локальной копии работает в отдельном worker.
После первого этапа она расширена [чтением пакетов и слепками](track-fingerprints.md).
Планирование и отдельные AV1/AAC-задания подключены следующим этапом —
[кодирование](encoding.md). B10/B13–B19 прошли
[итоговую приёмку T04](../tasks/T04-video-pipeline.md#итоговая-приёмка--2026-11-16);
[готовность владельца](readiness.md) подключена следующим этапом,
[постоянная очистка завершённых оригиналов](original-cleanup.md) подключена в B19.
Встроенные текстовые субтитры подключены [отдельным этапом B17](subtitles.md).
Превью и API выбора владельца подключены [отдельным этапом B16](thumbnails.md).

## Инварианты реализации

- Завершение/восстановление загрузки создаёт одну запись `video_source_processing`
  на upload_id и актуальное задание `video.inspect_source` в очереди `media`.
  Запись, задание и upload=uploaded фиксируются в одной транзакции PostgreSQL.
  В kwargs только числовой upload_id, без object key, заголовка, email или ссылок.
- Повтор подтверждения не создаёт новое видео/работу. Старые подтверждённые
  передачи без записи обработки подхватывает обслуживание загрузок; неподтверждённые
  multipart не попадают в media. Valkey и локальный диск не являются источником истины.
- Worker с одним тяжёлым слотом загружает закрытый серверный объект из RustFS
  в отдельный временный каталог, проверяет размер и запускает локальный ffprobe
  под ресурсным контролем ADR-0051. Полный исходник не проходит через HTTP FastAPI.
- Сохраняются выбранные технические поля всех дорожек, точный тайминг и SHA-256
  сжатых пакетов/конфигурации, без описательных тегов или входных URL.
  Подтверждённые слепки связаны с общими записями дорожек и состава исходника.
  Ни inspected, ни успешный ffprobe не означают processing=ready.
- Начало/завершение привязаны к токену запуска. Поздний результат старого worker
  не заменяет результат восстановленной работы: проверяются token, status=doing
  и номер попытки Procrastinate, в том числе до следующего claim.
  Повтор уже inspected — без эффекта.
- Ошибки сохраняются в журнале попыток, временные сбои повторяются по ADR-0035.
  Окончательный отказ имеет безопасный код в записи обработки; оригинал и
  публикация/видимость/дата изменения сохраняются. Ресурсные ошибки не повторяются
  с тем же бюджетом. Очередь может восстановиться после потери worker/Valkey.
- Тяжёлый процесс использует отдельный контейнер с CPU/RAM ADR-0051; обслуживание
  восстановления остаётся отдельно. Локальная копия удаляется только после
  завершения/остановки процесса; оригинал в RustFS этим этапом не удаляется.

## Код и эксплуатация

Миграции: [0005](../../backend/migrations/versions/0005_source_processing.py)
(источник/задание), [0006](../../backend/migrations/versions/0006_job_failure_codes.py)
(безопасный код ошибки в истории),
[0007](../../backend/migrations/versions/0007_source_attempt_fence.py) (номер попытки),
[0008](../../backend/migrations/versions/0008_track_fingerprints.py) (общие идентичности/связи).
План/общие кодированные дорожки добавляет
[0009](../../backend/migrations/versions/0009_media_encoding.py).
Порты/сценарии — [application/processing.py](../../backend/src/video/application/processing.py),
SQL — [infrastructure/processing.py](../../backend/src/video/infrastructure/processing.py),
SDK/ffprobe — [source_inspector.py](../../backend/src/video/infrastructure/source_inspector.py).

`SqlSourceJobs.admit` вызывается из общего восстановления подтверждённой передачи:
complete/refresh и обнаруженный cleanup завершённый объект создают работу в одной
транзакции с upload=uploaded. Задание добавляется через установленную функцию
Procrastinate 3.11.0 `procrastinate_defer_jobs_v1`; отдельного queue commit нет.
Repair забирает до 100 публикаций без записи обработки с SKIP LOCKED,
в том же порядке блокировок, что HTTP. Failed/aborted/cancelled queue jobs
сверяются с незавершённым состоянием источника.
Старые inspected без content_id или с отчётом версии 1/2 после succeeded задания повторно ставятся
в очередь одной транзакцией; активная работа не получает второе задание.

Процесс [app.media_worker](../../backend/src/app/media_worker.py), очередь `media`,
задача `video.inspect_source`: concurrency=1, heartbeat=10 с, три запуска,
задержки 30/120 с. Временные SDK/I/O/SQL-сбои повторяются, повреждённый ввод
и распознанные пределы — нет. Журнал middleware используется до решения о повторе.
`upload-maintenance` независимо проверяет обе очереди и переносит spool каждые 15 с;
отсутствие heartbeat 60 с фиксируется как worker_lost, затем повтор/окончательный отказ.

Сервисы `media-worker` и `media-tools` используют один
[docker/media-runtime.yml](../../docker/media-runtime.yml): CPU=2, RAM=8g,
без дополнительного swap и GPU, app, cap-drop/no-new-privileges, дисковый scratch.
У worker есть сеть для PostgreSQL/RustFS; у tools сети нет. В dev worker наследует
dev от base и bind-mount backend, prod собирается отдельно от того же base.
Рабочий каталог общий для одного слота; локальные данные не являются очередью
и не заменяют оригинал в RustFS.

При запуске фона `create_container(..., require_cache=False)` проверяет БД/бакет,
но не требует ping Valkey. Это внутренний режим DI, не HTTP/env-переключатель.
API сохраняет полный startup/readiness check, включая Valkey. media-worker
не ждёт Valkey в depends_on; отсутствие кэша не отменяет принятую работу.
У worker только три Compose Secrets: пароль PostgreSQL и два ключа RustFS.
`StorageSecrets` читает их отдельно; секреты Valkey/сессий/CSRF не монтируются
и не требуются для запуска. API сохраняет прежние проверки своих секретов.

```bash
./docker/run dev exec python alembic upgrade head
./docker/run dev up --build -d --wait media-worker upload-maintenance
```

API всё ещё требует сессию/CSRF и владение для передачи. Чтение служебной записи
и ID очереди не добавлены в публичные маршруты; существующий settings отражает
processing, без выдачи object_key, JobContext или сырых ошибок.

## Границы проверки ffprobe

Скачивание потоковое, порциями до 1 МиБ, без доверия расширению/имени клиента;
ContentLength и фактическое число байтов сверяются с подтверждённой передачей.
Дисковый контроль выполняется во время скачивания, общий deadline охватывает
скачивание и probe. Локальный исходник открыт сервером, наследуется только его FD:
ffprobe `-protocol_whitelist fd -fd N ... fd:` сохраняет seek, не разрешая
вложенные file/http/tcp URL. Проверено на загруженных concat-манифестах
с локальным файлом и HTTP-ловушкой; обращения к ним не происходят.
Отчёт XML пишется в собственный файл и читается порциями с освобождением узлов.
Непустой stderr при `-v error` означает отказ даже при exit=0; содержимое
stderr/пути/входные описательные теги в историю не попадают.

Первичные источники проверены 2026-11-14:
[ffprobe](https://ffmpeg.org/ffprobe.html) (select_streams, show_entries, -o),
[FFmpeg fd](https://ffmpeg.org/ffmpeg-protocols.html#fd) (seek по дескриптору),
[Procrastinate 3.11.0 schema](https://raw.githubusercontent.com/procrastinate-org/procrastinate/3.11.0/procrastinate/sql/schema.sql)
(постановка и поколения попыток).

После расширения проверяются все пакеты, состав дорожек, технические параметры,
поворот/цвет/HDR, аудио/субтитры и длительность по временной шкале пакетов.
Порог 3600 с проверяется без округления; превышение в заголовках также отклоняется.
Известные ошибки чтения/обрезки/повреждения не дают слепка; разбор сжатых пакетов
не доказывает декодируемость каждого кадра. Проверка декодером остаётся при
целевой конвертации. Подробности и ограничения — [слепки](track-fingerprints.md).

## Порядок этапа

Документ → миграция и ограничения → сценарии/порты → SQL/SDK/ffprobe/очередь
→ существующий контракт настроек/загрузки → проверки в Docker. Новых публичных
маршрутов нет, HTTP processing остаётся pending/processing/failed; первый успешный
этап не объявляет ready/partial. Итоговую готовность вычисляет
[следующий этап](readiness.md); защищённая выдача подключена в [B22](media-delivery.md).
Расширение использует версионированный формат `compressed-v1` и SHA-256
стандартной библиотеки; новых зависимостей нет.

## Приёмка первоначального этапа

Реальные PostgreSQL/RustFS/Procrastinate: commit/rollback задания вместе с исходником,
повтор и конкурентное подтверждение, восстановление старой загрузки, идемпотентный
повтор задания, ffprobe корректного и повреждённого файла/без видео,
ошибка объекта/размера, журнал и повторы, токен старого worker, потеря heartbeat,
сохранность исходника и независимых флагов публикации. Полная проверка длительности,
дедупликация и готовые качества этой приёмкой не подменяются.
