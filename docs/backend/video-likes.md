# Лайки видео

Дополнение R21: [взаимоисключающие дизлайки](video-dislikes.md) расширяют тот же
ответ личными disliked/can_dislike. Публичный счётчик остаётся только у лайков.

Реализованы сценарии и API B29 по [правилам Video](modules/video.md#лайки) и R02.
Вошедший зритель с обычным доступом к видео может установить/снять один лайк.
Команда задаёт целевое состояние, не переключает его вслепую. Автор видео
также может поставить лайк, поскольку имеет обычный доступ; роль сотрудника
не открывает недоступное private/hidden. Лайк не предоставляет разрешений.

## API

По R19 добавлен личный GET `/api/v1/videos/liked` с обычными правами просмотра
и порядком по времени текущего лайка — [контракт и проверка](library.md).
Миграция 0027 сохраняет created_at пары: повтор true не меняет дату,
снятие и новый лайк создают новую. Старые пары получают техническую дату миграции.

GET `/api/v1/videos/{id}/like` возвращает liked, like_count и can_like.
Доступ к объекту проверяется как при GET видео: published, visible, готовый
AV1/AAC-вариант и public либо вошедший владелец/приглашённый email.
Гость видит счётчик доступного public, liked=false/can_like=false; для вошедшего
с доступом can_like=true. Недоступный/отсутствующий объект — одинаковый 404,
без счётчика, признака прежнего лайка или частичных данных.

PUT того же пути принимает строгий bool liked и возвращает ту же структуру
после записи. Требуются вход, CSRF и свежий обычный доступ. Пользователь и
видео определяются сессией/URL, count/user_id/video_id из тела не принимаются
как источник состояния. Повтор установки/снятия идемпотентен.

Счётчик включает существующие лайки этой логической публикации, не других
публикаций общего физического медиа. Собственные liked и count читаются одним
агрегатом SQL. Лайки сохраняются до явного снятия; отзыв доступа/смена видимости
не являются командой отмены. Пока просмотра нет, обычные GET/PUT лайка закрыты,
включая снятие. Восстановление доступа не создаёт новый лайк и не теряет прежний.
Списки поставивших реакции и другие реакции не добавляются.

Ошибки: 401 для команды без действующего аккаунта, 404 без обычного доступа,
422 для неверного тела, общий 500 при сбое. Ответы no-store/Vary Cookie;
личность другого пользователя, email, внутренние ключи и детали SQL не выдаются.
Это единичное состояние и агрегат, не список; пагинация здесь не применяется.

## Реализация и приёмка

Схема 0021: video_likes с PK(video_id,account_id), FK на публикацию и аккаунт.
После R21 строка хранит reaction=like|dislike; отсутствие строки — оба false.
Снятие удаляет только совпадающий вид реакции. Счётчик рассчитывается
из строк PostgreSQL, без изменяемой копии/кэша, поэтому не может стать отрицательным.
Даты публикации/видео/канала/плейлиста не меняются. Новых библиотек, секретов,
ресурсных настроек и фоновых заданий нет.

Общая проверка просмотра выделена во внутренний VideoAccess и используется
GET видео и лайками внутри транзакции сценария. Streaming остаётся на прежних
защищённых маршрутах. PUT блокирует строку публикации перед проверкой доступа,
сериализуясь с изменением видимости/email-разрешений и другими командами лайка.
После ожидания проверка повторно читает актуальное состояние, затем записывает
пару и возвращает согласованный count/liked. Никакого SQL к таблицам User:
доверенный Viewer получается через существующий User.public-адаптер.

Проверены: 0/1/несколько лайков, повторы/параллельные команды одного и разных
пользователей, чужие пары/публикации и общий физический файл, rollback и FK/PK,
строгий bool/CSRF/подмена пользователя или счётчика, гость/владелец/приглашённый/
посторонний/user/moderator/admin, public/private/hidden/draft/нет готовности,
частичное готовое качество, отзыв до/во время ожидания блокировки, неизменность
дат/разрешений и сохранение без Valkey. Проверены счётчик без утечек и ложных
частичных ответов, регрессия обычного доступа/DI и настоящий Nginx dev/prod.
Интерфейс и его DOM-проверки — [готовый функциональный профиль F15](../frontend/video-likes.md).

разрешения/видимости/скрытия после commit и rollback изменяющей транзакции.
