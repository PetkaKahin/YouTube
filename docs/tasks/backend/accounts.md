# Аккаунты, сессии и роли

B01–B04 — `done`, B05 — `in_progress`: CLI назначения ролей и актуальность роли
готовы, ресурсные разрешения проверяются вместе с Video/Moderation.
Источники: [User](../../backend/modules/user.md),
[Channel: тег](../../backend/modules/channel.md), R06/R09.
Общие требования и зависимости — [реестр](README.md).

## Реализация B01–B05

Реализовано 2026-11-13; результаты проверок приведены ниже.

По дополнительному запросу пользователя добавлены Make-команды назначения ролей
и 34 интеграционные проверки гонок/безопасности по
[правилам тестирования](../../testing.md).
Изменения схемы БД, бизнес-логики, адаптеров хранения и контрактов API
для этого дополнения не потребовались.

По запросу пользователя цели по названиям ролей заменены
общими командами `make role get EMAIL=адрес` и
`make role set EMAIL=адрес ROLE=роль`. Для чтения добавлен сценарий GetRole
через User.public и вложенные команды `app.cli role get/set`.
Схема БД и HTTP-контракты не затронуты; допустимые роли определяет бэкенд.

- Идентификаторы аккаунта и канала — `bigint identity`, API `integer/int64`
  ([ADR-0029](../../decisions/0029-bigint-identifiers.md)).
- Таблица аккаунтов принадлежит User: имя, нормализованный email, Argon2-хеш,
  роль и дата создания. Таблица каналов принадлежит Channel: владелец, тег,
  дата создания. Канал один на аккаунт; email и тег имеют регистронезависимые
  уникальные ключи в PostgreSQL.
- Регистрацию координирует Channel.application: его адаптер обращается к
  User.public для создания аккаунта; оба адаптера получают одну REQUEST-сессию
  SQLAlchemy. Внешний сценарий открывает транзакцию и завершает её после создания
  канала; вложенный сценарий User делает flush без commit. Цикла User → Channel нет.
  Имена/теги/пароли проверяет домен; формат email — выбранный email-validator
  через порт, без DNS. Ошибки уникальности переводятся в ошибки полей.
- HTTP: POST `/api/v1/auth/register`, POST `/api/v1/auth/login`,
  GET `/api/v1/auth/me`, POST `/api/v1/auth/logout`. Регистрация без автоматического
  входа, как предусмотрено F05; login ротирует сессию. В сессии только user_id,
  актуальные данные и роль читаются из PostgreSQL при каждом обращении.
- CLI: `python -m app.cli role get -- EMAIL` читает роль,
  `python -m app.cli role set -- EMAIL ROLE` меняет её через сценарий User внутри Docker.
  Ресурсные права Video/Moderation проверяются при их реализации;
  назначение роли не добавляет обычный доступ к приватному видео.
  Make: `make role get EMAIL=адрес`, `make role set EMAIL=адрес ROLE=роль`.
- Проверки: доменные границы, повторы и конкуренция, откат регистрации,
  реальные PostgreSQL/Valkey, HTTP/CSRF/утрата сессии и актуальность роли.

### Конкуренция и безопасность дополнения

- 12 управляемых интеграционных гонок: конкурентные регистрации по email/тегу
  действительно ждут блокировку другой транзакции; это подтверждается
  `pg_blocking_pids` в текущей тестовой БД. Проверены commit владельца блокировки
  и потеря его соединения: проигравший получает конфликт либо ожидающий запрос
  успешно создаёт аккаунт после отката конкурента. Нет осиротевшего аккаунта.
- Параллельные смены роли сериализуются PostgreSQL. Отдельный HTTP-запрос видит
  последнюю подтверждённую роль, а не незавершённое повышение; после commit
  старая сессия получает окончательную роль. Login/me, задержанные на чтении БД,
  не оживляют старую сессию после logout или другой ротации. Начатый me может
  вернуть свой снимок 200, но не выставляет старую cookie; новый запрос проверяет
  актуальную сессию. Отмена регистрации и реальный разрыв её соединения
  откатывают обе записи, освобождают соединение и допускают повтор.
- 22 проверки безопасности: синтаксически допустимые SQL-последовательности
  в email проходят до реального репозитория; наблюдение SQL подтверждает bind-параметры.
  Вход не выбирает чужую строку, SetRole меняет только указанный аккаунт,
  обычная регистрация и вход остаются рабочими. SQL-последовательности в пароле
  и роли не дают входа/смены полномочий. HTML, шаблонные выражения, команды и пути
  в имени/теге отклоняются без создания аккаунта и резервирования тега.
- Проверены лишние user_id/owner_id/role/password_hash, поддельные заголовки
  авторизации, отсутствие публичного назначения ролей, неподписанный double-submit
  CSRF-токен и повреждённый субъект в серверной сессии: неверные типы/границы ID
  дают 401 до запроса к БД. Пароль, Argon2-хеш и токены отсутствуют в обычных телах
  ответов/журналах; email не попадает в журнал завершения запроса.
- Вместе с новыми тестами прошли существующие 18 гонок Q25 и 26 HTTP-проверок
  аккаунтов: **78 целевых проверок**, затем полный `make test`.
  Ruff/Formatter, Basedpyright и оба Tach проходят. `make audit` не обнаружил утечек
  на проверенных поверхностях. Make-команды отдельно проверены в Docker с перехватом
  argv: роли, отсутствие аргументов, кавычки/shell-метасимволы и вызов pytest.
  Разделитель `--` не позволяет трактовать email как опцию CLI.

Границы применимости: DOM/исполнение HTML проверяется при реализации фронтенда;
сейчас тестируется серверная валидация полей. У аккаунтов нет загрузки файлов,
пользовательских URL, путей к хранилищу и фоновых заданий — соответствующие SSRF,
медиаинъекции и сбои RustFS/worker относятся к будущим B-задачам. Согласованные
границы полей и срок сессий уже покрыты; новые пороги размера/частоты запросов
не вводились. Приватные видео/модерация остаются за сквозной приёмкой B05.

## B01. Зарегистрировать аккаунт и создать пустой канал

**Описание.** Посетитель создаёт аккаунт, с которым одновременно появляется его канал.

**Требования.** Принимаются имя, email, тег, пароль и повтор пароля.
Имя — 2–50 символов после удаления пробелов по краям; email — корректный формат,
без проверки существования ящика и без подтверждения. Email и тег уникальны без
учёта регистра. Пароль — 6–128 символов, Unicode/пробелы разрешены, trim и требования
к составу не применяются. Повтор точно совпадает и не сохраняется.
Тег после `@` — 3–30 символов из согласованного набора: латинские буквы, цифры,
точка, подчёркивание, дефис; `@` не учитывается в длине.
Роль нового аккаунта — user. Имя становится названием канала и именем автора
комментариев; одинаковые имена разрешены. Канал изначально не содержит видео/плейлистов.

**Приёмка.** Проверены границы 2/50, 3/30, 6/128 и превышения, неверные символы,
пустые поля, несовпадение паролей, дубли email/тега с другим регистром и конкурентная
регистрация. Успешный результат содержит ровно один аккаунт и его канал.
Сбой создания канала не выдаётся за успешную регистрацию; занятый тег не заменяется
автоматически. Клиент не назначает роль; пароль не хранится открытым текстом.

## B02. Войти по email и паролю

**Описание.** Зарегистрированный пользователь подтверждает личность для защищённых действий.

**Требования.** Вход использует email/пароль. Email сопоставляется по правилам регистрации;
пароль проверяется без изменения введённого значения. Успех создаёт новую действующую
сессию через выбранный готовый механизм; предыдущий анонимный идентификатор
не становится доверенным идентификатором авторизованной сессии.

**Приёмка.** Корректная пара позволяет обращаться от имени аккаунта; неверный пароль
или неизвестный email не дают сессии. Клиентский user_id/роль не меняют личность.
Повтор входа не создаёт новые аккаунты или каналы. Пароли и идентификаторы сессий
не раскрываются в диагностике и обычных данных профиля.

## B03. Поддерживать и продлевать серверную сессию

**Описание.** Активный пользователь остаётся в аккаунте, неактивный должен войти заново.

**Требования.** Серверные данные сессии находятся в Valkey, cookie содержит
непрозрачный идентификатор готовой библиотеки. Срок — 30 дней без активности;
использование действующей сессии согласованно продлевает cookie и серверный срок.
Истёкшая, неизвестная или утраченная сессия не восстанавливается одним продлением.
Роль и права не становятся бессрочно зафиксированными внутри сессии.
Для production обязательны согласованные безопасные cookie и готовая CSRF-защита
изменяющих браузерных запросов.

**Приёмка.** Проверены активность до истечения, 30 дней простоя, подмена cookie,
потеря Valkey и параллельные запросы. Гость не выполняет защищённые действия;
изменяющий запрос без требуемой CSRF-защиты отклоняется. Потеря сессий
не удаляет аккаунты/права/видео и не превращает запрос в привилегированный.

## B04. Выйти из аккаунта

**Описание.** Пользователь завершает текущую сессию.

**Требования.** Выход завершает серверную сессию и удаляет её cookie.
Завершённый идентификатор больше не авторизует запросы; одновременный запрос
не должен оживить завершённую сессию. Выход не удаляет аккаунт или его данные.

**Приёмка.** После выхода защищённые действия требуют входа даже со старой cookie.
Повторный выход и отсутствие сессии безопасны. Завершение текущей сессии
не вводит неописанную функцию управления всеми устройствами.

## B05. Назначать и применять роли

**Описание.** Уполномоченный оператор назначает роли существующим аккаунтам,
а система применяет их в бизнес-сценариях.

**Требования.** Роли — user/moderator/admin. Назначение — через CLI по email
существующего аккаунта, включая первого администратора; UI/публичного способа
самоназначения нет. Первый зарегистрированный пользователь остаётся user.
Moderator/admin получают согласованные возможности рассмотрения жалоб/скрытия;
роль не заменяет владение или отдельное разрешение на приватный просмотр.
Изменения роли учитываются и уже открытыми сессиями.

**Приёмка.** Неизвестный email/роль отклоняются, переданная клиентом роль игнорируется
как основание полномочий. После снятия роли старые сессии не сохраняют её через кэш.
Проверены права обычного пользователя, модератора и администратора, в том числе
отсутствие неограниченного обычного доступа сотрудников к приватным видео.
