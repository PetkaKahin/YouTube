## Согласованное направление

- Браузер загружает части напрямую в закрытый RustFS по временным подписанным
  ссылкам; FastAPI отвечает за разрешения и бизнес-сценарии, не принимает поток файла.
- Глобальная дедупликация по слепкам исходных дорожек и переиспользование
  совместимых готовых результатов, включая превью. У публикаций разные ссылки
  и независимые права. Общие готовые результаты живут до освобождения всех
  пользовательских ссылок; оригиналы временные по ADR-0040.
- Точный слепок SHA-256 считается сервером по сжатому содержимому дорожек,
  точному таймингу и значимым параметрам без предварительного полного декодирования.
  Подтверждённый дубль не кодируется повторно. Описательные теги в постоянные
  медиа не переносятся, технические свойства сохраняются.
- Фоновые задания — Procrastinate/PostgreSQL; Valkey не влияет на сохранность очереди.
- Готовые видеоварианты — только AV1, SVT-AV1 preset 6, для малых сторон libaom;
  отдельное [кодирование реализовано](../backend/encoding.md).
  [ADR-0039](../decisions/0039-av1-encoding.md).
  Оригинал временный по [ADR-0040](../decisions/0040-temporary-originals.md);
  он сохраняется до завершения всех зависимых работ, включая повторы, затем удаляется.

Основания: ADR-0030–0034 в [реестре решений](../decisions/README.md).
Бизнес-требования — [B08–B12](backend/upload.md), [B13–B19](backend/processing.md),
правила доступа — [B20–B22](backend/access.md).

## Техническая проверка Procrastinate

Закреплён Procrastinate 3.11.0 и обновлён uv.lock. В Docker с Python 3.14.10,
Psycopg 3.3.9 и PostgreSQL прошли семь проверок `tests/test_procrastinate.py`:

- Постановка через то же соединение SQLAlchemy: до commit задание невидимо
  другому worker; rollback удаляет и тестовые данные, и задание; commit сохраняет оба.
- Одновременная постановка с одним queueing_lock принимает ровно одно задание,
  отклоняет дубликат и выполняет принятый экземпляр.
- Ограниченные повторы заканчиваются состоянием failed в PostgreSQL.
  Для 3.11.0 проверено: RetryStrategy(max_attempts=1) даёт два запуска,
  max_attempts=2 — три. Первый запуск предшествует счётчику этих повторов.
- Закрытие и повторное открытие приложения очереди не теряет задание;
  SQL-последовательность в payload остаётся данными и не меняет схему.
- Worker в отдельном процессе принудительно завершается SIGKILL после
  подтверждённого побочного эффекта. Зависшее задание обнаруживается и вручную
  возвращается в очередь через API библиотеки, затем успешно завершается.
  Идемпотентный эффект с уникальным ключом не дублируется.

Схема библиотеки и служебная таблица существуют только в отдельной тестовой БД,
которая удаляется после прогона. Короткие уникальные имена тестовых очередей
укладываются вместе с префиксом библиотеки в лимит PostgreSQL LISTEN/NOTIFY.
Секрет PostgreSQL читается из Compose Secret file, не передаётся через argv/environment.

Числа попыток, размеры пула, concurrency и нулевой порог heartbeat в этих тестах
служат проверке библиотеки; это не подключённая конфигурация production worker.
На этапе квалификации automatic recovery и production worker ещё не подключались.
Позднее миграция 0004 и worker обслуживания загрузок подключены (ниже).
Идемпотентность будущих бизнес-эффектов должна быть реализована
в сценариях; Procrastinate не даёт гарантии однократного эффекта сам по себе.

## Постоянный журнал ошибок

После согласования хранения Q36 добавлены миграция 0002 и технический журнал
в `common`: независимые транзакции PostgreSQL, постоянный файловый буфер,
идемпотентный перенос и middleware Procrastinate. Отказ БД оставляет безопасное
событие на томе; отказ самого буфера останавливает приём работы worker.
Очищаемые записи очереди не владеют историей ошибок.
Поля, ограничения, способы подключения и границы —
[диагностика заданий](../backend/background-jobs.md),
[ADR-0036](../decisions/0036-durable-job-error-history.md).

Новые проверки `tests/test_job_errors.py` и `tests/test_job_monitor.py` используют
изолированные БД с миграциями и реальный Procrastinate. Проверены разрыв соединения,
независимость от отката задачи, рестарт буфера, сбой после commit до удаления файла,
запись из нескольких процессов, конкурентные переносы с подтверждёнными
блокировками PostgreSQL, отмена во время commit, отказ fsync, повреждённые записи,
подмена ID/симлинк, отсутствие секретов в JSON и логах, все неудачные попытки
sync/async-задач перед успехом/окончательной ошибкой и сохранность после очистки очереди.
Наблюдатели блокировок используют AUTOCOMMIT, чтобы обновлять статистику
новых соединений при каждом опросе, а не удерживать снимок одной транзакции.
Этап не добавляет HTTP/браузерных входов; проверки прав/CSRF и медиалимитов
остаются до соответствующих сценариев. Подготовлен формат события потери worker
без выдуманного traceback; затем оно подключено к worker обслуживания загрузок.
