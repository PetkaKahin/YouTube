# T02: технический фундамент бэкенда

Последнее дополнение: защита конкурентных сессий вне starsessions по
[ADR-0028](../decisions/0028-session-concurrency.md), `done`, Q25 закрыт.
Обновлены документация, адаптер хранения, HTTP-обёртка и проверки. Этапы БД,
бизнес-логики и прикладных маршрутов не затронуты. Актуальный результат — в последнем разделе;
предыдущие разделы сохраняют проверки соответствующих уточнений.

Статус: `done` (актуально на 2026-11-13), включая перенос структуры и настройку Tach по
[ADR-0023](../decisions/0023-module-boundaries.md). Основание: техническая основа перед бизнес-реализацией,
[ADR-0020](../decisions/0020-backend-libraries.md),
[ADR-0022](../decisions/0022-http-foundation.md).

## Объём и порядок

1. Документация: зафиксировать HTTP-контракт и параметры защиты.
2. БД: подготовить SQLAlchemy/Psycopg и среду Alembic. Бизнес-таблицы,
   пустая начальная миграция и автоматическое `create_all` не требуются.
3. Бизнес-логика: сценарии B01–B36 не затронуты; общая граница авторизации
   не должна зависеть от HTTP или конкретной библиотеки политик.
4. Инфраструктура: выбранные зависимости, настройки из environment/secret-файлов,
   подключение PostgreSQL, Valkey, RustFS; открытие/закрытие ресурсов в lifespan;
   подготовка сессий, CSRF, хеширования и адаптера Casbin.
5. HTTP: фабрика приложения, агрегатор `/v1`, служебная проверка готовности,
   middleware запроса/ответа, единые ошибки и схемы, Swagger/OpenAPI.
6. Тесты в Docker: строгие типы/игнорирование полей, ошибки без секретов,
   middleware и завершение ресурсов, работа подключений, библиотек защиты,
   Alembic и обязательные проверки качества.

## Приёмка

- Swagger работает через Nginx, OpenAPI описывает общие ошибки.
- Ошибки HTTP/валидации/CSRF/непредвиденные сбои возвращают общий формат.
- Каждый запрос получает серверный `request_id`; журнал завершения содержит
  статус и длительность, без пользовательского ввода и секретных значений.
- Ресурсы закрываются при остановке и частично неудачном запуске.
- Транзакции принадлежат будущим сценариям, middleware не делает commit.
- ORM и HTTP не становятся зависимостями внутренних слоёв; Tach проверяет
  существующие границы. Границы будущих модулей добавляются при их создании.
- Доступ по умолчанию запрещён; аутентификационные и ресурсные политики
  B-задач не объявляются реализованными.

## Уточнение public (2026-11-13, ADR-0024)

Статус уточнения: `done` (2026-11-13). Меняются только ограничения импортов,
архитектурные проверки и документы; этапы БД, бизнес-логики, инфраструктурных
адаптеров и HTTP-контрактов не затронуты. `public` разрешены только собственные

В этом уточнении сборка конкретных модулей ещё не реализовывалась; вопрос Q29
позднее закрыт ADR-0027, описанным в последнем дополнении ниже.

сторонних библиотек для `public`. Разрешение сборки через `public` и положительный
тест импорта infrastructure удалены; вместо них проверяются все пять модулей,
общие технические пакеты, чужие публичные интерфейсы и внешние библиотеки.
Также исправлен тестовый помощник: проверки `migrations`/`tests` теперь изменяют
реальные копии этих source roots и проверяют успешный импорт `public` и отказ
при импорте инфраструктуры. Ранее ошибочно создавались похожие пути под `src`.

Полный `docker/run check`: 121 тест прошёл, оба аудита Tach выполнены,
Basedpyright — 0 ошибок/предупреждений; Ruff/Formatter, аудит зависимостей,
проверки фронтенда и HTTP smoke — успешно. Runtime-код и Docker-сборки
этим уточнением не менялись; результаты сборок и prod-проверки выше относятся
к этапу переноса от 2026-11-12.

## Конкурентные сессии (2026-11-13, ADR-0028)

Статус: `done`, Q25 закрыт. Пользователь выбрал расширение starsessions вне пакета.
Проверены свежие PyPI/GitHub: стабильная 2.2.1 и предварительная 2.3.0a1;
в alpha и основной ветке исправления безусловного SET нет. Версия сохранена.

Добавлены независимый контракт `ManagedSessionStore`, `GuardedRedisStore` в общей
инфраструктуре и HTTP-обёртка `GuardedSessionMiddleware`. Наши helpers используют
публичные функции starsessions; исходники библиотеки, генератор ID, сериализация
и формат cookie не заменяются. Ротация выполняет атомарный перенос существующей
записи, создание использует NX, обновление — XX. Отклонённая запись не выдаёт
сессионную cookie. Ошибочные ответы не сохраняют новые данные сессии.

БД, бизнес-сценарии и прикладные маршруты не затронуты. Уже отправленные ответы
и начатые сценарии не отменяются отзывом; точные границы — в ADR-0028.

Проверено в Docker:

- `docker/run check`: 203 теста, включая 18 новых проверок сессий и 137
  архитектурных. Ruff/Formatter, Basedpyright, Tach, uv/npm audit, фронтенд
  и HTTP smoke прошли; известных уязвимостей зависимостей не найдено.
- Управляемые событиями гонки: позднее чтение/сохранение против выхода и ротации,
  две ротации, поздний выход; TTL/удаление до записи, потеря резервирования ID,
  недоверенная cookie, неуспешная аутентификация, отмена, поток и ошибки Valkey.
  Использованы два независимых экземпляра middleware и настоящий Valkey.
- Dev/prod Python собраны. Production wheel проверен настоящим HTTP-сервером:
  создание, чтение, ротация и завершение сессии, Secure/HttpOnly/SameSite cookie,
  readiness, Swagger/OpenAPI, Alembic и завершение lifespan. pytest в prod нет.
- `docker/run audit dev`: 43 поверхности, утечек не найдено. Все четыре
  BuildKit-контекста проверены: secret-файлы и значения исключены.
- Проверены 76 Markdown-файлов и 611 локальных ссылок; файловых целей без
  соответствующих файлов нет. Подготовленный индекс Git проверен на значения
  Compose Secrets; утечек нет. `git diff --check` — без замечаний.
