# YouTube

Учебная копия YouTube для ПК и мобильного веба в тёмной теме.
Бэкенд — Python/FastAPI, фронтенд — Vue 3/TypeScript. Разработка, установка
зависимостей, сборка и проверки выполняются в Docker.

Сейчас доступны регистрация с пустым каналом, вход, выход, текущий аккаунт
и управление ролями через CLI. В API доступны черновики и настройки владельца,
прямая загрузка в RustFS, фоновый конвейер AV1/AAC/WebVTT/WebP, публикация,
email-разрешения, защищённая раздача Nginx и главная лента.
Интерфейс пока представляет собой пустую тёмную страницу.
Работу аккаунтов можно проверить через Swagger UI.
Для черновиков используйте POST `/api/v1/videos`, для настроек — GET/PUT
`/api/v1/videos/{id}/settings`. Требуются вход и CSRF для изменяющих запросов.
Название обязательно (1–100 символов), описание необязательно (до 5000),
видимость задаётся явно (`public`/`private`). Создание черновика не загружает файл.
Для передачи файла вызовите POST `/api/v1/videos/{id}/upload` с размером `size`.
Ответ содержит ссылки PUT для частей; отправляйте байты по этим ссылкам,
затем вызовите POST `/api/v1/videos/{id}/upload/{upload_id}/complete`.
Ссылки обновляются через POST `.../{upload_id}/refresh`.
Сервис `upload-maintenance` очищает незавершённые передачи и сохраняет ошибки.
Публикация подтверждается POST `/api/v1/videos/{id}/publish`; готовые качества
открываются с учётом прав — [доставка медиа](docs/backend/media-delivery.md).
Главная доступна через GET `/api/v1/videos/feed`: ответ содержит `items` (до 20)
и `next_cursor`. Для продолжения передайте курсор в query-параметре `cursor`;
null означает конец выдачи. [Контракт ленты](docs/backend/feed.md).
Поиск видео и каналов: GET `/api/v1/search?q=текст`, необязательные `type`, `sort`,
`duration`, `period`, повторяемый `feature` и `cursor`.
Запрос — 1–100 символов, порция до 20; [контракт поиска](docs/backend/search.md).
Плейлисты: POST `/api/v1/playlists`, GET `/api/v1/playlists/mine`,
GET `/api/v1/playlists/{id}`. Выбор набора для своего видео — GET/PUT
`/api/v1/videos/{id}/playlists`. Режимы public/unlisted/private;
право открыть плейлист не заменяет права его видео — [контракт](docs/backend/playlists.md).

## Установка и запуск

Понадобятся Git, Docker Engine с BuildKit, Docker Compose 2.24+, Bash и GNU Make.
Устанавливать Python, Node, npm, uv и FFmpeg на хост не требуется.
Обязательной видеокарты и GPU-драйверов хоста нет: медиазависимости настроены
в Docker на CPU, включая программный Vulkan Mesa/Lavapipe.

Склонируйте репозиторий и перейдите в его корневой каталог. При первом запуске:

```bash
cp .env.example .env
```

Перед запуском настройте несекретные значения в `.env`. Например, если порт
8080 занят, задайте `HTTP_PORT=18080`. Существующий `.env` повторно копировать
из примера не нужно.

Подготовьте окружение и запустите контейнеры:

```bash
make init
make up
```

`make init` готовит окружение, создаёт недостающие secrets и lock-файлы внутри
Docker. Существующие значения secrets сохраняются. `make up` собирает и
запускает dev, затем дожидается готовности сервисов.

Перед работой с аккаунтами примените миграции:

```bash
./docker/run dev exec python alembic upgrade head
```

Миграции не выполняются автоматически при старте приложения.
Запланированный короткий вариант этой команды — `make migrate`;
такой цели в Makefile пока нет.

Адреса при `HTTP_PORT=8080`:

| Что открыть | Адрес |
| --- | --- |
| Приложение | http://localhost:8080 |
| Swagger UI | http://localhost:8080/docs → /api/docs |
| OpenAPI | http://localhost:8080/api/openapi.json |
| API | http://localhost:8080/api/v1 |
| RustFS Console в dev | http://localhost:9001 |

Порты HTTP и RustFS настраиваются в `.env`. PostgreSQL и Valkey доступны
внутри Docker-сети. Пароли и ключи хранятся в локальном `docker/secrets/`
и передаются через Compose Secrets; в Git их добавлять нельзя.
`.env.example` содержит только несекретные настройки.

| Команда | Назначение |
| --- | --- |
| `make help` | Список реализованных команд |

| `make up` | Собрать образы, запустить dev и дождаться готовности |
| `make start` | Поднять dev без принудительной пересборки |
| `make build` | Собрать образы dev |

## Роли пользователей

Сначала создайте аккаунт через регистрацию в Swagger UI. Все новые аккаунты
получают роль `user`; первый пользователь не становится администратором автоматически.

У изменяющих API-запросов есть CSRF-защита: после открытия Swagger скопируйте
значение cookie `csrftoken` из браузера в поле `CSRFToken` кнопки **Authorize**.
Поля регистрации и входа показаны в схемах операций `/api/v1/auth/...`.

Прочитать роль существующего аккаунта:

```bash
make role get EMAIL=user@example.com
```

Назначить роль модератора или администратора:

```bash
make role set EMAIL=user@example.com ROLE=moderator
make role set EMAIL=user@example.com ROLE=admin
```

Вернуть обычную роль:

```bash
make role set EMAIL=user@example.com ROLE=user
```

Доступны только `user`, `moderator`, `admin`. Команды выполняются в
Python-контейнере; неизвестный аккаунт или недопустимая роль отклоняются.
Через тот же CLI назначается первый администратор. UI управления ролями нет.

## Миграции БД

После запуска dev доступны команды Alembic внутри Docker:

```bash
# Применить все миграции.
./docker/run dev exec python alembic upgrade head

# Узнать текущую ревизию.
./docker/run dev exec python alembic current

# Проверить, требуется ли миграция для изменений моделей.
./docker/run dev exec python alembic check

# Создать миграцию после изменения моделей.
./docker/run dev exec python alembic revision --autogenerate -m "add_video"
```

Созданный файл в `backend/migrations/versions/` нужно проверить перед применением.

Для Makefile запланированы следующие команды; **они ещё не реализованы**:

| Будущая команда | Назначение |
| --- | --- |
| `make migrate` | Применить миграции до последней ревизии |
| `make migration-status` | Показать текущую ревизию БД |
| `make migration-check` | Проверить соответствие моделей схеме миграций |
| `make migration NAME=add_video` | Создать миграцию с заданным названием |

## Тестовые и демонстрационные данные

Запланированная команда — **`make seed`**: заполнить БД данными для ручного
тестирования и просмотра реализованных сценариев приложения после миграций.
**Сидеры и эта цель Makefile пока не реализованы.** Состав данных будет определён
при их разработке; готовых демонстрационных аккаунтов, паролей и видео сейчас нет.

Пока для ручной проверки создавайте аккаунты через регистрацию в Swagger
и назначайте нужные роли командами выше. Запуск автоматических тестов не
является наполнением рабочей dev-БД: интеграционные проверки аккаунтов
используют отдельную временную БД и удаляют её после прогона.

## Проверки

Для работающего dev:

```bash
make test           # Тесты бэкенда.
make check          # Проверки кода, зависимости, тесты, сборка и HTTP.
make audit          # Поиск утечек секретов в dev.
make context-check  # Проверка исключений секретов и артефактов из сборки.
```

Требования к функциональным проверкам, безопасности, инъекциям и лимитам —
[правила тестирования](docs/testing.md). Результаты проверок и технические
подробности находятся в [документации](docs/README.md).

## Архитектура

Бэкенд — модульный монолит с модулями `user`, `channel`, `video`, `comment`,
`moderation`. Внутри модулей — clean architecture: `domain` содержит правила,
`application` — сценарии и порты, `infrastructure` — адаптеры и ORM.
Модули обращаются друг к другу через `public`.

`backend/src/app/` собирает приложение и содержит HTTP-контроллеры/CLI;
`common/` предоставляет общие технические средства. Зависимости связывает
Dishka через явный реестр провайдеров. Бизнес-тесты находятся внутри модулей,
общие и HTTP-тесты — в `backend/tests/`.

Фронтенд — Vue 3 + TypeScript + Vite, архитектура FSD. Vue Router отвечает
за навигацию, Pinia — за клиентское состояние, TanStack Query — за серверные
данные, Hey API — за клиент из OpenAPI. UI должен повторять YouTube в рамках ТЗ.

| Компонент | Ответственность |
| --- | --- |
| PostgreSQL | Постоянные бизнес-данные и очередь обработки |
| Valkey | Потеряемые кэш и серверные сессии |
| RustFS | Закрытое объектное хранилище медиа |
| Nginx | Единый HTTP-вход, статика в prod, прокси Vite в dev и API |
| FFmpeg | Фоновая обработка видео в варианты HLS |

Compose-файлы лежат в корне, конфигурации контейнеров — в `docker/`.
Dockerfile Python/Node/Nginx имеют стадии `base`, `dev`, `prod`;
`dev` и `prod` напрямую наследуются от `base`. Реализованы приём исходника
и worker обслуживания загрузок; FFmpeg-конвейер ещё не подключён.

Подробнее: [бэкенд](docs/backend/architecture.md),
[фронтенд](docs/frontend/architecture.md), [Docker](docs/infrastructure/docker.md).
