# Документация

## Перед работой

Если по текущей задаче есть неразрешённые вопросы, сначала задай их пользователю
и дождись ответа, затем выполняй зависимую работу. Проверь документы и прошлые
ответы. Не превращай предложение в принятое решение и не расширяй ТЗ.
Можно записать известные факты и явно открытые вопросы без выбора ответа.
Разбирай вопросы небольшими связанными порциями. После ответа фиксируй принятое
решение и возникающие из него новые вопросы; новые вопросы тоже требуют разбора
с пользователем, а не молчаливого выбора ответа.
На текущем этапе обсуждай только бизнес-правила. Новые вопросы о деталях UI
переноси на этап разработки интерфейса, о библиотеках — на технический этап.

Начни с [карты документации](../../docs/README.md), затем прочитай только нужную
область и её ссылки. Источник объёма — [ТЗ](../../docs/project/requirements.md).
Все пути здесь относительны этому `SKILL.md`.

## Что и где фиксировать

- Назначение и краткий контекст — [project/overview.md](../../docs/project/overview.md).
- Экраны и границы функциональности — [project/requirements.md](../../docs/project/requirements.md).
- Стек, архитектура и правила модулей — в `docs/backend/` и `docs/frontend/`.
- Запуск и эксплуатация — в `docs/infrastructure/`.
- Важное устойчивое решение с причиной и последствиями — в `docs/decisions/`.
- Задачи, зависимости, критерии готовности и статус — в `docs/tasks/`.

## Как поддерживать

- Пиши по-русски, кратко и предметно: ответственность, инварианты, связи,
  ограничения, место в коде, актуальные команды и способы проверки.
  Документ должен отвечать на рабочие вопросы без повторного поиска по всему коду.
- Разделяй требования пользователя, базовую спецификацию в рамках ТЗ, предложения
  и фактически реализованное. Для изменяемых внешних правил указывай первичный
  источник и дату проверки. Описывай только нужную проекту часть поведения YouTube.
- Храни правило в одном документе; из остальных давай ссылку. Скиллы направляют
  к документации, а не дублируют стек и бизнес-правила целиком.
- Веди документы по областям и бизнес-модулям. Добавляя файл, обновляй ближайший
  индекс. Не создавай пустые шаблоны и не превращай документацию в журнал чата.
- При расхождении кода и документов проверь затронутые файлы и выясни причину.
  Код подтверждает текущее поведение, но не отменяет требование пользователя.
- Не называй запланированные пути существующими, команды — рабочими, проверки —
  пройденными без фактических оснований. Выполненная задача содержит результат
  и проверку; принятый ADR меняется новой записью, если меняется само решение.
- Перед завершением проверь относительные ссылки, согласованность статусов,
  отсутствие дубликатов правил и функций за пределами ТЗ.

## Результат

Верни ссылки на основные изменения, перечисли существенные открытые вопросы
и сообщи результат проверки документов. Документация не должна требовать чтения
всего репозитория для продолжения одной задачи.
