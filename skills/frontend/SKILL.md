# Фронтенд

## Перед работой

Сначала прочитай имеющиеся ответы и документы, чтобы не спрашивать повторно.
Если по текущей задаче остались неразрешённые вопросы, задай их пользователю
и сразу останови всю работу над текущей задачей до получения ответа.
После вопроса не продолжай даже независимые части задачи, не редактируй файлы
и не запускай проверки. Передай ход пользователю; ожидание по таймауту, молчание
или собственное предположение не заменяют ответ. Если ответ требует уточнения,
снова задай вопрос и остановись. Не придумывай отсутствующие бизнес-правила,
API или визуальные референсы; уточняй только вопросы, влияющие на текущую задачу.

Прочитай [индекс фронтенда](../../docs/frontend/README.md),
[архитектуру FSD](../../docs/frontend/architecture.md), нужный экран из
[описания экранов](../../docs/frontend/screens.md) и правила его бизнес-модуля
по [индексу бэкенда](../../docs/backend/README.md).
Проверь [ТЗ](../../docs/project/requirements.md) и
[открытые вопросы](../../docs/tasks/open-questions.md).
Пути здесь относительны этому `SKILL.md`; пути к коду в документах — корню проекта.

## Выполнение

- Соблюдай FSD: зависимости направлены вниз по слоям, слайсы изолированы,
  внешние импорты проходят через их публичный API. Создавай только нужные слои и слайсы.
- Для соответствия YouTube используй согласованные референсы ровно нужных экранов.
  Сходство интерфейса не разрешает добавлять функции вне ТЗ или неработающие кнопки.
- Поддерживай ПК и мобильный веб в тёмной теме. Выноси цвета и размеры в токены;
  переключатель темы и другие темы сейчас не реализуются.
- Получай типы и клиент через Hey API из OpenAPI бэкенда; не редактируй генерацию
  вручную. Отсутствующий контракт сначала согласуй, не выдавай фиктивные данные за интеграцию.
- TanStack Query для Vue владеет серверными данными, Pinia — клиентским состоянием;
  не храни одни и те же списки в двух местах. Учитывай очистку приватных данных при
  смене пользователя, выходе, потере сессии и отказе в доступе.
- Показывай загрузку файла и обработку на сервере как разные состояния.
  Предлагай только готовые качества HLS. Приватность проверяет бэкенд,
  скрытие кнопки или route guard не заменяет проверку прав.
- Выполняй необходимые проверки сборки, типов, линтинга и форматирования
  в Docker в объёме текущей задачи по правилам ниже. Проверяй затронутые сценарии
  на размерах ПК и телефона, состояния ошибок и клавиатурную доступность.
  Не добавляй тесты, повторяющие разметку.

## Проверки

- После отдельной задачи запускай только её профильные тесты и необходимые
  проверки затронутых файлов, сценариев и непосредственно изменённых интеграций.
  Включай применимые проверки безопасности, ошибок и границ из
  [правил тестирования](../../docs/testing.md).
- Остальные части приложения после каждой задачи не проверяй. Полный набор
  тестов и общие проверки приложения, включая `make check`, запускай один раз
  после завершения всех задач выполняемого плана, на итоговом состоянии.
  Для закрытия отдельной задачи достаточно её применимых проверок.
- Успешные проверки повторяй только при новых изменениях, влияющих на результат,
  либо после исправления найденного сбоя; автоматически прогон не расширяй.
- Если меняется только документация, проверяй только затронутые документы по
  скиллу [docs](../docs/SKILL.md#проверки), без тестов и сборок приложения.

## Результат

Обнови документы затронутого экрана, интеграции и задачу по правилам
[docs](../docs/SKILL.md). Укажи проведённые проверки и ограничения.
